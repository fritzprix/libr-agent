# 서브 에이전트 · 오케스트레이션

> 한 대화(세션)가 다른 대화를 **자식(하위 에이전트)** 으로 띄워 일을 나누는 기능입니다.  
> 병렬·파이프라인·팀 같은 패턴은 번들 **오케스트레이션 스킬**로 고릅니다.

---

## 서브 에이전트란?

|                   | 설명                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **무엇인가**      | 부모 세션이 만든 **자식 세션**. 부모–자식 관계가 히스토리에 남습니다.                                                      |
| **무엇이 아닌가** | 부모를 그대로 복제한 클론이 **아닙니다**. 기본은 **별도 작업 폴더**이며, 로컬 스킬·폴더 규칙도 자동으로 복사되지 않습니다. |
| **누가 쓰나**     | 보통 `@skill:delegate` 같은 스킬을 붙이면 에이전트가 위임·진행·결과 합치기를 관리합니다.                                   |

부모는 가능하면 **쉬는 중인 같은 역할의 자식**을 다시 쓰고, 필요할 때만 새 자식을 만듭니다. 흐름은 **맡기기 → 진행 확인 → 추가 지시 → 결과 합치기**입니다.  
형제 자식끼리는 직접 대화하지 않고, 부모가 중계합니다.

위임할 때 **작업 난이도**(쉬움 / 보통 / 높음)를 고를 수 있습니다. **Settings → AI & Models → Sub-Agent Model Routing**에서 난이도별 모델을 지정할 수 있고, 비어 있으면 부모·기본 모델을 따릅니다. 가능한 한 낮은 난이도를 고르세요.

### UI에서 보는 곳

| 화면               | 내용                                                                                |
| ------------------ | ----------------------------------------------------------------------------------- |
| **Chat / History** | 세션 카드에 하위 에이전트 개수. 삭제 시 **모두 삭제** vs **이것만 삭제(하위 유지)** |
| 사이드바 **Org**   | **명시적으로 만든 팀**만. 일회성 위임은 여기 안 나옵니다                            |

![Org view](../assets/screenshots/guides/org.png)

**Org 내보내기 · 가져오기**: Org 화면에서 팀을 `.libragent-org` 번들 파일로 내보내 다른 PC로 옮기거나 백업할 수 있습니다. 각 Org 카드의 **Export Org**로 저장할 폴더를 고르고, 화면 상단의 **Import Org**로 번들 파일을 선택합니다. 가져오기는 기존 항목과 **병합**하며, API 키 같은 민감 정보는 포함되지 않습니다. 암호화된 번들은 아직 이 화면에서 가져올 수 없으니 암호 없이 내보낸 번들을 사용하세요.

## 작동 방식 한눈에 보기

```text
              ┌────────────────── 부모 세션 ──────────────────┐
              │ ① 목표를 쪼개고  ② 맡기고  ③ 진행 확인  ④ 합치고  ⑤ 검수 │
              └───────┬───────────────┬───────────────┬───────┘
                      ▼               ▼               ▼
                 자식 세션 A      자식 세션 B      자식 세션 C
              (각자 어시스턴트·작업 폴더·난이도)  ← 형제끼리는 대화하지 않음
```

부모는 아래 **내장 도구**로 자식을 다룹니다. 직접 호출할 필요는 없고, 스킬을 붙이면 에이전트가 알아서 순서대로 사용합니다.

| 하는 일                            | 내장 도구                                                              | 알아둘 점                                                                           |
| ---------------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 어떤 어시스턴트·세션이 있는지 조회 | `agent__listAgents`                                                    | 위임 전에 **쉬는 중인 같은 역할의 자식**이 있는지 먼저 봅니다                       |
| 새 자식 만들기                     | `agent__spawnSession`                                                  | `waitForResult=true`면 끝날 때까지 기다리고, `false`면 부모가 다른 일을 계속합니다  |
| 기존 자식에게 새 일 주기·추가 지시 | `agent__messageToSession`                                              | `reset=true`면 이전 대화·계획은 비우되 **작업 폴더 파일은 유지**                    |
| 진행·결과 확인                     | `agent__checkSession`                                                  | `wait=true`면 끝날 때까지 대기. 결과에 작업 폴더가 `SHARED`인지 `ISOLATED`인지 표시 |
| 멈추기                             | `agent__stopSession`                                                   | 응답 없는 자식을 중단                                                               |
| 컨텍스트 압축 · 정리               | `agent__compactSessionContext`, `agent__deleteSession`                 | 긴 세션을 줄이거나 쓰지 않는 자식을 정리                                            |
| 전문 어시스턴트 만들기·수정        | `agent__createAgent`, `agent__updateAgent`                             | `recruit`·`boost`가 사용                                                            |
| 팀 준비 · Org 만들기               | `agent__prepareTeamworkWorkspace`, `agent__createOrg`, `agent__getOrg` | `teamwork`·`org`가 사용                                                             |

### 자식은 이렇게 결과를 돌려줍니다

- 자식의 **마지막 응답 텍스트**가 결과입니다. 자식의 스크래치패드 메모는 부모에게 **보이지 않습니다**.
- 그래서 “파일에 저장했어요”만 돌아오면 `ISOLATED` 상태에서는 부모가 읽을 수 없습니다. 위임할 때 **산출물을 최종 답변 본문에 담도록** 요구하거나, 폴더를 공유하세요.
- 부모는 자식의 “완료/테스트 통과” 주장을 **가설**로 취급하고 직접 확인합니다 ([품질 검증](#품질-검증-위임-결과를-믿기-전에) 참고).

### 난이도 선택 (complexity)

위임·추가 지시마다 `low` / `normal` / `high`를 고릅니다. **Settings → AI & Models → Sub-Agent Model Routing**에서 난이도별 모델을 지정해 두면, 단순 조사에는 가벼운 모델을, 어려운 설계에는 강한 모델을 자동으로 쓸 수 있습니다. 비워 두면 부모·기본 모델을 따릅니다.

### 동시 실행과 한도

- 동시에 **활성** 상태인 세션은 기본 **4개**까지입니다(일시 중단된 세션은 기본 8개까지 유지). 병렬 패턴은 이 한도에 맞춰 묶음(batch)으로 띄웁니다.
- 세션 계보에는 **깊이(depth)** 와 **팬아웃(fanout, 한 부모의 자식 수)** 한도를 둘 수 있고, 넘으면 위임이 오류로 거절됩니다. 자식이 또 자식을 무한히 만드는 일을 막는 안전장치입니다.

## 꼭 기억할 격리 규칙

자식은 기본적으로 **자기 작업 폴더**를 씁니다. 부모 폴더의 파일이 자동으로 따라가지 않습니다.

- 같은 폴더의 결과물을 함께 보고·고치려면, 위임할 때 **「지금 쓰는 작업 폴더를 그대로 쓰라」**고 말하세요.
- 폴더 안 규칙 파일·프로젝트 전용 스킬은 **자식이 쓰는 폴더** 기준으로 읽힙니다.
- **이 어시스턴트**에만 둔 스킬은 자식에 고른 어시스턴트를 따릅니다.
- **내 계정 전체** 스킬은 부모·자식 모두 쓸 수 있습니다.
- 다른 경로를 쓰려면 세션의 **작업 폴더 재정의**로 지정합니다.
- 자식에게 **대화만 초기화**하라고 하면 이전 대화·계획은 비우지만 폴더 파일은 남습니다. 브라우저 탭 상태까지 유지하려면 초기화하지 말고 이어서 지시하세요.

부모가 임시로만 가진 파일이나 규칙을 자식이 “당연히” 안다면 위임이 실패하기 쉽습니다. 넘길 때 **목표·범위·산출물 형식·필수 경로**를 적거나, **같은 작업 폴더를 재사용**하라고 명시하세요.

세부 운영은 `@skill:delegate` 안내를 따르면 됩니다.

## 언제 어떤 스킬을 쓰나

입력에 `@skill:이름`을 붙이거나, 에이전트에게 패턴 이름을 말해 주세요.

### 1) 한 번 위임 · 기본

| 스킬           | 이럴 때                                                    |
| -------------- | ---------------------------------------------------------- |
| **`delegate`** | 자식에게 맡기고 지켜보며 결과를 받는 **기본기**            |
| **`recruit`**  | 새 **전문 어시스턴트**를 만들고 싶을 때 (위임 자체는 아님) |
| **`boost`**    | **이미 있는** 어시스턴트 도구를 정리·보강할 때             |

```
@skill:delegate
이 리포의 auth 모듈만 읽고 취약점 후보를 Markdown으로 요약해줘.
```

### 2) 작업 나누기 (일회성 자식)

| 스킬                       | 패턴        | 한 줄                                   |
| -------------------------- | ----------- | --------------------------------------- |
| **`divide-conquer`**       | 병렬 분할   | 겹치지 않는 조각을 나눠 합침            |
| **`hub-spoke`**            | 허브–스포크 | 중앙이 워커만 지휘·병합                 |
| **`pipeline`**             | 순차 조립   | A 결과 → B 입력 → C …                   |
| **`consensus-delegation`** | 다관점 합의 | 같은 질문을 여러 관점으로 → 부모가 조율 |
| **`gatekeeper`**           | 품질 게이트 | 작성 ↔ 리뷰 루프                       |
| **`pair-programming`**     | 페어        | 두 역할이 **같은 작업 폴더**에서 턴제   |

```
@skill:divide-conquer
프론트·백엔드·문서 점검 리포트를 병렬로 나눠 작성한 뒤 하나로 합쳐줘.
```

```
@skill:consensus-delegation
이 PR의 보안·성능·유지보수 관점을 각각 검토하고 의견을 조율해줘.
```

### 3) 지속 팀 · Org

일회성 위임과 다릅니다. **팀 구성**과 **Org 화면**이 필요할 때입니다.

| 스킬                  | 역할                                                   |
| --------------------- | ------------------------------------------------------ |
| **`teamwork`**        | 태스크포스 설계·역할 준비. **먼저** 사용               |
| **`org`**             | Org에 보이는 멤버 세션 만들기. 재개는 **Org 루트**에서 |
| **`org-restructure`** | 이미 있는 Org의 역할·규칙을 고칠 때                    |

흐름: `teamwork`로 준비 → `org`로 팀 만들기 → 사이드바 **Org**에서 이어하기 → 구조 변경은 `org-restructure`.

- **Org** ≠ 예약 작업(`schedule`) ≠ 세션 안 리마인더(`loop`) ≠ 완료 후 깨우기(`call-me-back`)
- 일반 위임만으로는 **Org** 목록에 안 뜹니다

```
@skill:teamwork
리서치·구현·리뷰 3역할 태스크포스를 만들고 hub-spoke로 조율해줘.
```

## 패턴 자세히 보기

아래 각 패턴은 번들 스킬이 실제로 따르는 절차를 사용자 관점으로 정리한 것입니다. 더 많은 실전 예시는 [오케스트레이션 실전 예시](orchestration-examples.md)를 보세요.

### `delegate` — 기본기

1. 위임이 맞는지 판단(범위가 분명하거나, 병렬 가능하거나, 전문 어시스턴트가 필요할 때)
2. 쉬는 중인 같은 역할의 자식이 있으면 **재사용**, 없으면 새로 생성
3. 자식이 볼 **작업 폴더**를 정함 — 기본은 격리, 같은 파일을 봐야 하면 “현재 작업 폴더 공유”
4. 목표·범위·출력 형식·필수 경로가 담긴 **자급자족 지시** 작성
5. 진행을 확인하고 필요하면 추가 지시, 마지막에 결과를 합침

잘 쓴 요청의 모양:

```text
@skill:delegate
auth 모듈(src/auth/**)만 읽고 취약점 후보를 찾아줘.
- 범위: 코드 수정 금지, src/auth 밖은 보지 말 것
- 출력: 최종 답변에 "심각도 | 파일:줄 | 설명 | 제안" 표로
- 현재 작업 폴더를 그대로 공유해서 일해줘
```

### `divide-conquer` — 겹치지 않는 조각을 병렬로

**분해 → 배정 → 띄우기 → 감시 → 병합 → 검증**의 6단계입니다. 조각끼리 서로의 결과가 필요하면 이 패턴이 아니라 `pipeline`입니다.

- 조각은 **겹치지 않아야** 합니다(같은 파일을 두 자식이 고치면 충돌).
- 같은 폴더를 공유하면 자식마다 **고유한 파일명·하위 폴더**를 쓰게 하세요.
- 병합 뒤에는 빌드·테스트로 **통합 검증**을 하고, 실패한 조각만 다시 시킵니다.

```text
@skill:divide-conquer
docs/ 의 한국어 가이드 12개를 영어로 번역해줘. 4개씩 3묶음으로 나눠 병렬로,
용어집(docs/glossary.md)을 공통 규칙으로 따르고, 끝나면 링크가 깨지지 않았는지 검증해줘.
```

### `hub-spoke` — 중앙 조율자 + 전문 워커

허브가 계획·작업 목록·병합을 맡고, 스포크(워커)는 **허브와만** 소통합니다. A의 결과가 B에 필요하면 허브가 A의 산출물 요약을 B에게 전달합니다.

- 허브가 모든 대화 로그를 읽지 않도록 **요약 보고와 파일 목록**만 받게 합니다(컨텍스트 폭주 방지).
- 코드 작업은 허브 작업 폴더를 공유하고, 조사·집필은 최종 답변 본문으로 받습니다.

```text
@skill:hub-spoke
신규 결제 모듈 도입을 검토해줘. 허브는 너(조율), 스포크는 ①시장·가격 조사 ②기술 연동 난이도 ③법규·보안 체크.
스포크 결과는 각각 1페이지 요약으로 받아 최종 비교표와 추천안을 만들어줘.
```

### `pipeline` — 단계가 이어지는 조립 라인

`조사 → 초안 → 리뷰 → 정리`처럼 앞 단계 산출물이 뒤 단계의 입력입니다. 모든 단계가 **같은 작업 폴더**를 쓰고, 다음 단계에는 대화 전체가 아니라 **요약 + 파일 경로**만 넘깁니다. 단계가 실패하면 그 단계만 재시도합니다.

```text
@skill:pipeline
"로컬 에이전트 도입 사례" 블로그 글을 만들어줘.
1단계 자료 조사(출처 5개 이상) → 2단계 개요·초안 → 3단계 팩트·톤 리뷰 → 4단계 최종 Markdown 정리.
각 단계 산출물은 drafts/ 폴더에 저장.
```

### `consensus-delegation` — 같은 질문, 서로 다른 시각

2~4명의 자식이 **같은 범위·같은 출력 양식**으로 각자 독립 검토합니다(예: 보안·성능·유지보수). 자식끼리는 서로 모르며, 부모가 결과를 비교해 **의견이 갈리는 지점만** 추가 질문으로 조율합니다. 투표 알고리즘이 있는 것이 아니라, 부모가 근거를 따져 종합합니다.

각 자식에게 요구하는 공통 양식:

```text
Verdict: approve | approve-with-caveats | reject | inconclusive
Confidence: high | medium | low
Findings: - [발견]: [근거: 경로·줄·명령 출력]
Risks:    - [위험]: [왜 중요한가]
```

팁: 관점마다 어시스턴트를 새로 만들지 말고, 기존 어시스턴트에 “당신은 보안 리뷰어로 검토합니다”처럼 **지시문으로 관점**을 주입하세요.

### `gatekeeper` — 작성 ↔ 검수 품질 게이트

작성자가 제출하면 검수자가 기준표로 **승인/반려**합니다. 반려 시 실패 항목과 고칠 점이 작성자에게 전달되어 재작업합니다. 사소한 문체 차이로 무한 반복하지 않도록 부모가 **최대 재작업 횟수(기본 3회)** 를 지킵니다.

```text
@skill:gatekeeper
릴리스 노트 초안을 작성자에게 맡기고, 검수자는 ①사실 오류 없음 ②사용자 영향 먼저 ③한 항목 2문장 이내
기준으로 심사해줘. 3회 안에 통과 못 하면 남은 문제를 정리해서 알려줘.
```

### `pair-programming` — 운전자와 항법사

두 자식이 **같은 작업 폴더**에서 번갈아 일합니다. 운전자(Driver)는 구현하고 변경 요약을 남기며, 항법사(Navigator)는 파일/`git diff`를 읽고 구조·버그를 짚어 다음 지시를 줍니다. 부모가 턴을 중계하고, 테스트를 쓰는 단계에서는 **역할을 교대**합니다.

```text
@skill:pair-programming
src/utils/date.ts 의 시간대 버그를 고쳐줘. 운전자는 구현, 항법사는 diff 리뷰.
수정 후 테스트 작성 단계에서는 역할을 바꿔서 진행해줘.
```

## 품질 검증: 위임 결과를 믿기 전에

중요한 작업은 `delegate` 뒤에 **`delegation-eval-loop`** 를 붙이세요. **자식은 만들고, 부모가 합격을 판정**하는 구조입니다.

1. **계약 먼저** — 위임 전에 목표, 허용/금지 경로, 체크박스 **합격 기준**(`- [ ] 테스트 통과` 등), 결과를 어디에 담을지 정합니다.
2. **4단계 검증** (앞에서 실패하면 바로 반려)

   | 단계           | 확인                                   | 방법                                         |
   | -------------- | -------------------------------------- | -------------------------------------------- |
   | 1. 결정적      | 빌드·타입·테스트·린트                  | 부모가 같은 명령을 실행하거나 원본 출력 확인 |
   | 2. 불변 조건   | 허용 경로 밖 수정 여부                 | `git status` / `git diff --stat`             |
   | 3. 경로·신뢰성 | 실제로 실행했는가, 중단·취소·증거 없음 | 결과 텍스트와 실행 흔적 대조                 |
   | 4. 의미        | 사용자 의도·예외 상황 충족             | 앞 단계를 통과한 뒤 부모가 판단              |

3. **구체적으로 반려** — “다시 해” 대신 실패 로그를 그대로 전달해 재지시합니다.
4. **횟수 제한** — 3~5회 반복해도 안 되면 진단 정보와 함께 사용자에게 에스컬레이션합니다.

```text
@skill:delegate @skill:delegation-eval-loop
payments/ 의 반올림 버그를 고쳐줘.
- 허용 경로: src/payments/**, tests/payments/**  (그 외 수정 금지)
- 합격 기준: - [ ] pnpm test payments 통과  - [ ] 새 회귀 테스트 1개 이상
- 최종 답변에 실행한 명령과 원본 출력을 붙일 것
```

## 시간·이벤트 기반 기능과의 구분

이름이 비슷해 보여도 쓰임이 다릅니다. 위임(`delegate`)이나 Org가 **아닙니다.**

| 필요                                                                 | 스킬               | 특징                                                               |
| -------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------ |
| “5분 뒤에 알려줘”, “매일 아침 확인” — **지금 대화 안에서** 시간 기반 | `loop`             | 이 세션을 정해진 시각에 다시 깨움                                  |
| “빌드가 끝나면 깨워줘”, 웹훅·티켓 상태                               | `call-me-back`     | 시간이 아닌 **완료 신호**로 이 세션을 재개                         |
| 앱을 닫아도 도는 cron 자동화                                         | `schedule`         | 세션과 무관한 **전역** 예약 작업 ([예약 작업](scheduled-tasks.md)) |
| 오래 가는 멀티 에이전트 팀                                           | `teamwork` → `org` | Org 화면에 표시, 루트 세션에서 재개                                |

---

## 지속 팀(Org) 운영 흐름

1. **`teamwork`** — 정말 여러 갈래의 일인지 먼저 판단합니다(한 에이전트로 되면 팀을 만들지 않음). 미션·역할·조율 방식을 정하고 앱 전용 폴더에 헌법 파일(`MISSION.md`, `ROLES.md`, `agents.md`, `coordination/` 등)을 준비합니다. 조율 방식은 **순차(Sequential)**, **허브–스포크**, **스웜(공유 보드 기반 자율 탐색)** 중 하나를 고릅니다.
2. **`org`** — 루트 세션에서 Org를 한 번 만들고, 멤버를 **Org 소속으로** 띄웁니다. 멤버는 팀 작업 폴더를 그대로 상속합니다. 나중에 **Org 루트**에서 이어 하며, 특정 자식 세션을 재개하는 것은 Org 재개가 아닙니다.
3. **`org-restructure`** — 팀을 해체하지 않고 역할 추가·제거·병합, 규칙 수정, 담당자 재배정을 합니다.
4. **`postmortem-improve`** — 미션이 끝났거나 같은 실패가 반복될 때 교훈을 정리하고 `org-restructure`·`boost`·`recruit`로 개선을 연결합니다.

Org는 [내보내기·가져오기](#ui에서-보는-곳)로 다른 PC에 옮길 수 있습니다.

## 빠른 선택 표

| 하고 싶은 일                    | 추천                               |
| ------------------------------- | ---------------------------------- |
| 한 자식에게 맡기고 결과만 받기  | `@skill:delegate`                  |
| 큰 일을 독립 조각으로 병렬 처리 | `@skill:divide-conquer`            |
| 중앙이 여러 워커를 배분·통합    | `@skill:hub-spoke`                 |
| 단계가 순서대로 이어짐          | `@skill:pipeline`                  |
| 같은 안건을 여러 관점으로       | `@skill:consensus-delegation`      |
| 작성 ↔ 엄격 리뷰 루프          | `@skill:gatekeeper`                |
| 두 에이전트가 코드 페어         | `@skill:pair-programming`          |
| 오래 가는 팀 + Org 화면         | `@skill:teamwork` → `@skill:org`   |
| 전문 어시스턴트 새로 뽑기       | `@skill:recruit` (이후 `delegate`) |
| 기존 어시스턴트 도구 다이어트   | `@skill:boost`                     |

스킬이 누구에게 적용되는지는 [스킬 가이드](skills.md)를 보세요.

## 사용 팁

1. **가장 작은 구조**부터 — 한 에이전트로 되면 팀을 만들지 마세요.
2. **넘기는 내용을 자급자족**으로 — 자식이 부모 대화를 추측하지 않게.
3. **병렬일 때는 부모가 다른 일도 할 수 있게** — 스킬이 안내하는 비동기 위임을 따릅니다.
4. **자식 결과를 확인**한 뒤 최종 답으로 쓰세요.
5. **세션 삭제** 시 하위까지 지울지 History에서 고르세요.
