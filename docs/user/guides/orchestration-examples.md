# 오케스트레이션 실전 예시

> [서브 에이전트 · 오케스트레이션](sub-agents.md)의 패턴을 일상 업무에 쓰는 방법입니다.  
> 요청 문장을 복사해서 내용만 바꿔 쓰세요.

## 먼저, 필요한 만큼만

한 에이전트로 충분하면 **맡기지 마세요**. 일이 나뉘거나, 다른 시선이 필요하거나, 오래 이어질 때만 구조를 키웁니다. 작게 시작하고, 결과는 확인한 뒤에 쓰는 것이 LibrAgent의 기본 원칙입니다.

| 상황                               | 쓰는 스킬                           |
| ---------------------------------- | ----------------------------------- |
| 한 덩어리를 다른 에이전트에게 맡김 | `delegate`                          |
| 서로 상관없는 일이 여러 개         | `divide-conquer`                    |
| 앞 단계의 결과가 다음 단계의 재료  | `pipeline`                          |
| 같은 안건을 여러 관점으로          | `consensus-delegation`              |
| 대표 한 명이 전문가들을 지휘       | `hub-spoke`                         |
| 만들고, 검수하고, 반복             | `gatekeeper` ([세션 루프](loop.md)) |
| 오래 가는 팀과 Org 화면            | `teamwork` → `org`                  |

---

## 예시 1. 다른 시선으로 검토받기 (`delegate`)

**이럴 때**: 내가 쓴 문서를 "내가 아닌 다른 눈"으로 검토받고 싶을 때.

```text
@skill:delegate
지금 폴더의 proposal.md를 투자자 입장에서 읽고 검토해줘.
- 이 폴더를 함께 쓰고, 파일은 고치지 마
- 답변에 "좋은 점 3개 / 부족한 점 3개 / 꼭 물어볼 질문 5개"로 정리해줘
```

**일어나는 일**: 에이전트가 검토 담당 자식을 찾거나 새로 만들고, 자식이 문서를 읽고 답변으로 결과를 돌려줍니다. 부모는 범위를 지켰는지 확인하고 결과를 전해 줍니다.

**주의**: 자식이 "파일을 찾을 수 없어요"라고 하면 작업 폴더가 따로인 것입니다. "이 폴더를 함께 써줘"라고 말하거나, 내용을 요청에 붙여 넣어 다시 시키세요. "다른 눈으로 검토"를 부탁했는데 부모가 스스로 평가했다면 다시 요청하세요.

---

## 예시 2. 여러 조각을 동시에 처리하기 (`divide-conquer`)

**이럴 때**: 서로 상관없는 일을 한꺼번에 하고 싶을 때.

```text
@skill:divide-conquer
이번 분기 보고서를 세 조각으로 나눠 동시에 작성해줘.
① 매출 요약 ② 고객 의견 정리 ③ 다음 분기 계획
각 조각은 report 폴더에 따로 저장하고, 마지막에 하나의 SUMMARY.md로 합쳐줘.
```

**일어나는 일**: 에이전트가 겹치지 않게 세 조각으로 나누고, 조각마다 다른 파일 이름을 줍니다. 자식 셋이 동시에 일하는 동안 부모는 합칠 준비를 합니다. 끝나면 결과를 합치고, 부실한 조각만 다시 시킵니다.

**주의**: 조각이 같은 폴더를 쓰면 **파일 이름을 달리** 하세요. 합친 뒤 "요약이 각 조각과 어긋나지 않는지" 확인해 달라고 하면 더 안전합니다.

## 예시 3. 글 한 편을 단계별로 쓰기 (`pipeline`)

**이럴 때**: 앞 단계의 결과가 뒤 단계의 재료가 될 때.

```text
@skill:pipeline
"로컬 에이전트로 주간 보고서 만들기" 블로그 글을 써줘.
1) 조사: 출처 5개 이상, drafts/01-조사.md에 정리
2) 초안: 조사를 바탕으로 drafts/02-초안.md
3) 검토: 사실과 말투를 확인하고 고칠 점을 drafts/03-검토.md에
4) 마무리: 검토를 반영한 최종본 final.md
```

**일어나는 일**: 모든 단계가 같은 폴더를 쓰고, 다음 단계에는 대화 전체가 아니라 요약과 파일 위치만 전달됩니다. 검토에서 문제가 나오면 초안 단계만 다시 합니다.

**주의**: 단계끼리 상관이 없으면 `pipeline`보다 `divide-conquer`가 빠릅니다.

## 예시 4. 하나의 결정을 여러 관점으로 보기 (`consensus-delegation`)

**이럴 때**: 새 서비스 도입처럼 중요한 결정을 비용, 위험, 사용 편의 관점으로 나눠 따져 보고 싶을 때.

```text
@skill:consensus-delegation
팀 메신저를 새 서비스로 바꿀지 검토해줘.
비용 / 위험(보안·이전 부담) / 사용 편의 세 관점으로 각각 따로 검토하고,
모두 같은 양식(결론, 확신 정도, 발견한 점, 위험)으로 답하게 해줘.
의견이 다른 부분만 다시 물어서 최종 추천(바꾼다 / 조건부로 바꾼다 / 유지한다)을 내줘.
```

**결과 예시**

| 관점      | 결론        | 핵심 근거                            |
| --------- | ----------- | ------------------------------------ |
| 비용      | 조건부 찬성 | 연 비용은 줄지만 이전 작업 비용이 큼 |
| 위험      | 조건부 찬성 | 자료 이전 중 보안 점검 필요          |
| 사용 편의 | 반대        | 팀원 절반이 새 화면에 익숙하지 않음  |

부모는 "비용은 좋은데 편의가 나쁘다"처럼 **부딪히는 부분만** 해당 자식에게 다시 묻고, 최종 추천에 근거를 붙입니다.

**주의**: 관점은 요청에 **역할로 적어 주면** 됩니다. 어시스턴트를 따로 만들 필요가 없습니다. 2~4개 관점이 적당합니다.

## 예시 5. 대표가 전문가들을 지휘하기 (`hub-spoke`)

**이럴 때**: 조사, 분석, 정리가 서로 다른 일인데 한 명이 모아서 결론을 내야 할 때.

```text
@skill:hub-spoke
경쟁 서비스 3곳(A, B, C)의 비교 보고서를 만들어줘.
대표는 너야. 일하는 사람은 ① 기능 비교 ② 가격 비교 ③ 이용자 평가 정리야.
각자 1페이지 요약과 출처 링크를 대표에게만 보고하게 해.
대표는 요약만 받아서 비교표와 "우리가 배울 점 3가지"를 써줘.
```

**일어나는 일**: 대표가 할 일 목록을 만들고 전문가들이 동시에 일합니다. ②의 결과가 ③에 필요하면 대표가 요약을 전달합니다. 전문가끼리는 직접 말하지 않습니다.

**주의**: 대표가 전문가의 긴 대화 기록을 모두 읽게 하면 일을 못 합니다. "요약과 파일 목록만 받아"라고 적어 두세요.

## 예시 6. 만들고, 검수하고, 다시 만들기 (`gatekeeper`)

**이럴 때**: 공지문이나 안내문이 정해진 기준을 꼭 지켜야 할 때.

```text
@skill:gatekeeper
작성자가 이번 달 고객 공지문을 쓰게 해줘.
검수자는 ① 사실 오류 없음 ② 고객에게 중요한 내용이 맨 앞 ③ 항목마다 두 문장 이하를 확인해줘.
3번 안에 통과하지 못하면 남은 문제를 알려줘.
```

**일어나는 일**: 검수자가 기준표로 통과 또는 반려를 정하고, 반려하면 고칠 점이 작성자에게 전달됩니다. 최대 3번까지 반복하고, 그래도 안 되면 이유를 정리해 알려 줍니다.

**주의**: 기준을 **구체적으로** 적으세요. "좋게 써줘"처럼 모호하면 끝나지 않는 반복이 됩니다.  
시계로 깨워 작성·검수로 할 일을 도는 법은 [세션 루프 (loop)](loop.md)를 보세요.

## 예시 7. 결과를 믿기 전에 확인시키기 (`delegate` + `delegation-eval-loop`)

**이럴 때**: "다 했어요"라는 말이 아니라 **확인된 결과**가 필요할 때.

```text
@skill:delegate @skill:delegation-eval-loop
고객 안내문의 날짜 표기를 모두 "2026년 3월 5일" 형식으로 통일해줘.
- 고쳐도 되는 곳: notice 폴더 (다른 곳은 고치지 마)
- 합격 기준: - [ ] 모든 날짜가 같은 형식  - [ ] 날짜가 아닌 숫자는 그대로
- 바꾼 파일 목록과 바꾸기 전후 예시 3개를 답변에 써줘
```

**일어나는 일**: 부모가 자식 작업이 끝나면 합격 기준을 직접 확인하고, 건드리면 안 되는 곳이 바뀌었는지 봅니다. 문제가 있으면 구체적으로 돌려보내고, 3~5번 해도 안 되면 이유와 함께 알려 줍니다.

**주의**: 자식의 "문제없어요"는 증거가 아닙니다. 중간에 멈춘 일이나 증거 없는 "완료"는 실패로 봅니다.

## 예시 8. 오래 가는 팀 만들기 (`teamwork` → `org`)

**이럴 때**: 몇 주에 걸쳐 같은 팀이 일하고, 한곳에서 상태를 보고 싶을 때.

```text
@skill:teamwork
"월간 시장 동향 보고서" 팀을 만들어줘.
역할은 조사 담당, 데이터 분석 담당, 편집자야. 대표가 조율하는 방식이 좋겠어.
결과물은 매달 reports 폴더에 월별 파일로 남기고, 편집자가 마지막에 승인해줘.
```

준비가 끝나면 이어서 말합니다.

```text
@skill:org
방금 준비한 팀으로 Org를 만들고 조사 담당부터 시작시켜줘.
```

**일어나는 일**: 에이전트가 목표와 역할, 일하는 규칙을 정리해 팀 규칙으로 저장하고, Org를 만들어 팀원을 소속시킵니다. 사이드바 **Org**에 팀이 나타나고, 다음 달에는 **Org의 대표 대화**에서 이어서 합니다.

나중에 팀을 고칠 때:

```text
@skill:org-restructure
데이터 분석 담당을 조사 담당과 합치고, 편집자의 승인 기준을 역할 설명에 추가해줘.
```

**주의**: 한 번만 맡기는 일은 Org에 나타나지 않습니다. 정해진 때마다 반복하고 싶으면 Org가 아니라 [예약 작업](scheduled-tasks.md)을 쓰세요. 팀을 다른 컴퓨터로 옮기려면 Org 화면의 **Export Org / Import Org**를 쓰세요.

## 예시 9. 끝나기를 기다리기 (`call-me-back` / `loop`)

위임이 아니라 **기다림**이 필요한 경우입니다.

```text
@skill:call-me-back
이 폴더의 사진을 모두 변환하는 작업을 백그라운드로 시작해줘.
끝나면 이 대화에서 이어서, 실패한 파일이 있는지 알려줘.
```

```text
@skill:loop
30분 뒤에 이 일이 끝났는지 다시 확인해줘.
```

- 작업이 **끝나기**를 기다림 → `call-me-back` ([안내](call-me-back.md))
- **시간**이 지나면 다시 봄 → `loop` ([세션 루프 안내](loop.md)), 앱을 닫아도 돌아야 하면 `schedule`

## 흔한 실수와 해결

| 증상                             | 이유                           | 해결                                                       |
| -------------------------------- | ------------------------------ | ---------------------------------------------------------- |
| 자식이 파일을 못 찾음            | 자식의 작업 폴더가 따로임      | "이 폴더를 함께 써줘"라고 말하거나 내용을 요청에 붙여 넣기 |
| 부모가 자식의 결과를 못 읽음     | 자식이 파일에만 저장함         | "결과를 답변에 직접 써줘"라고 요청                         |
| 여러 자식이 서로의 파일을 덮어씀 | 같은 파일 이름을 씀            | 자식마다 다른 파일 이름이나 하위 폴더 지정                 |
| 자식이 계속 새로 생김            | 쉬는 자식을 다시 쓰지 않음     | "쉬고 있는 같은 역할의 자식을 다시 써줘"라고 요청          |
| 새 자식을 못 만든다는 알림       | 안전 한도를 넘음               | 자식이 또 자식을 만들지 않게 하거나 구조를 단순하게        |
| 병렬 작업이 느림                 | 동시에 일하는 수에 한도가 있음 | 일을 더 작은 묶음이나 단계로 나눔                          |
| 검수가 끝나지 않음               | 합격 기준이 모호함             | 체크리스트와 최대 반복 횟수 지정                           |
| 한 번 맡긴 일이 Org에 안 보임    | 정상 동작임                    | Org가 필요하면 `teamwork` → `org`                          |

더 많은 해결 방법은 [문제 해결](troubleshooting.md)을 보세요.
