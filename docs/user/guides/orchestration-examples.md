# 오케스트레이션 실전 예시

> [서브 에이전트 · 오케스트레이션](sub-agents.md)의 패턴을 실제 상황에 맞춰 쓰는 방법입니다.  
> 프롬프트는 그대로 복사해 값만 바꿔 쓰세요. 각 예시는 **언제 / 프롬프트 / 내부에서 일어나는 일 / 결과 / 주의**로 구성했습니다.

먼저 고르는 법: 한 에이전트로 충분하면 **위임하지 마세요**. 병렬·독립 검토·장기 팀이 필요할 때만 구조를 올립니다.

```text
한 에이전트로 충분?            → 그냥 대화
한 덩어리를 따로 맡기고 싶다   → delegate
독립된 조각 여러 개            → divide-conquer
앞 단계 결과가 다음 입력       → pipeline
같은 안건, 여러 시각           → consensus-delegation
중앙이 여러 전문가를 지휘      → hub-spoke
만들고 → 엄격 검수 반복        → gatekeeper
오래 가는 팀 + Org 화면        → teamwork → org
```

---

## 예시 1. 독립 리뷰어 하나에게 맡기기 (`delegate`)

**언제**: 내가 만든 결과물을 “내가 아닌 다른 눈”으로 검토받고 싶을 때.

```text
@skill:delegate
현재 작업 폴더의 docs/proposal.md 를 투자자 관점에서 검토해줘.
- 현재 작업 폴더를 공유해서 파일을 직접 읽을 것
- 수정하지 말고, 최종 답변에 "강점 3 / 약점 3 / 반드시 물어볼 질문 5"로 정리
```

**내부에서 일어나는 일**

1. 부모가 쉬는 중인 리뷰어 자식이 있는지 확인 → 없으면 새로 생성(작업 폴더 **공유**)
2. 자식이 파일을 읽고 최종 답변으로 결과 반환
3. 부모가 결과의 `workspace: SHARED` 여부와 범위를 확인하고 그대로 전달

**주의**: 자식이 “파일을 찾을 수 없다”고 하면 폴더가 **격리**된 것입니다. 공유를 명시하거나 내용을 지시문에 붙여 넣어 다시 시키세요. 요청이 “독립 검토”인데 부모가 대신 자기 평가를 내놓았다면 다시 요청하세요.

## 예시 2. 모듈별 병렬 점검 (`divide-conquer`)

**언제**: 프론트·백엔드·문서처럼 서로 독립된 점검을 한꺼번에 하고 싶을 때.

```text
@skill:divide-conquer
리포를 세 조각으로 나눠 병렬 점검해줘.
① src/ui/**  접근성·렌더링 문제
② src-tauri/** 에러 처리·unsafe 사용
③ docs/**  깨진 링크·오래된 설명
각 조각은 report/<조각이름>.md 에 저장하고, 마지막에 하나의 report/SUMMARY.md 로 병합.
수정은 하지 말고 발견 사항만 보고.
```

**내부에서 일어나는 일**

1. 부모가 겹치지 않는 3조각으로 분해하고 각 자식에게 고유한 출력 파일명을 배정
2. 활성 세션 한도(기본 4) 안에서 자식 3개를 **비동기**로 띄움 — 부모는 기다리는 동안 병합 틀을 준비
3. `agent__checkSession`으로 각 자식 완료를 확인하고 결과를 병합
4. 비어 있거나 부실한 조각만 해당 자식에게 추가 지시

**주의**: 조각이 파일을 공유하면 서로 덮어쓰지 않도록 **파일명을 분리**하세요. 병합 뒤 “요약이 각 보고서와 모순되지 않는지” 한 번 더 확인하도록 요청하면 안전합니다.

## 예시 3. 글 한 편을 단계별로 (`pipeline`)

**언제**: 앞 단계 산출물이 뒤 단계의 입력이 되는 작업.

```text
@skill:pipeline
"로컬 에이전트로 주간 리포트 자동화하기" 블로그 글을 만들어줘.
1) 조사: 출처 5개 이상, drafts/01-research.md 에 요약+링크
2) 초안: 01을 바탕으로 개요와 본문, drafts/02-draft.md
3) 리뷰: 사실·톤 점검 결과와 수정 제안, drafts/03-review.md
4) 정리: 리뷰 반영한 최종본 final.md
각 단계는 이전 단계의 파일 경로와 요약만 받아서 진행해.
```

**내부에서 일어나는 일**: 모든 단계가 같은 폴더를 공유하고, 다음 단계에는 대화 전체가 아니라 **요약 + 경로**만 전달됩니다. 3단계에서 문제가 나오면 2단계만 재작업을 지시합니다.

**주의**: 단계가 서로 독립이면 `pipeline`이 아니라 `divide-conquer`가 더 빠릅니다.

## 예시 4. PR을 여러 관점으로 (`consensus-delegation` + `delegation-eval-loop`)

**언제**: 병합 전에 보안·성능·유지보수 시각을 비교하고, 의견이 갈리면 조율하고 싶을 때.

```text
@skill:consensus-delegation
PR #1234 (diff: git diff main...HEAD) 를 세 관점으로 각각 독립 검토해줘.
- 보안 / 성능 / 유지보수성
- 모두 같은 양식(Verdict · Confidence · Findings · Risks)으로 답할 것
- 코드는 수정 금지, 현재 작업 폴더 공유
의견이 갈리는 항목만 추가로 물어서 최종 권고(병합 / 조건부 병합 / 반려)를 내줘.
```

**결과의 모양(예)**

| 관점     | Verdict              | 핵심 근거                               |
| -------- | -------------------- | --------------------------------------- |
| 보안     | approve-with-caveats | 입력 검증 누락 1건 (`api/upload.ts:42`) |
| 성능     | approve              | 신규 쿼리 인덱스 사용 확인              |
| 유지보수 | reject               | 300줄 함수, 테스트 부재                 |

부모는 “reject vs approve” 충돌 지점(유지보수 vs 성능)만 해당 자식에게 되물어 조율하고, 최종 권고에 각 근거를 연결합니다.

**주의**: 관점은 **지시문**으로 주입하세요(어시스턴트를 새로 만들 필요 없음). 패널은 2~4명이 적당합니다.

## 예시 5. 중앙 조율자가 전문가를 지휘 (`hub-spoke`)

**언제**: 조사·분석·초안처럼 역할이 다른 일을 한 명이 통합해야 할 때.

```text
@skill:hub-spoke
경쟁 제품 3개(A, B, C) 비교 보고서를 만들어줘.
허브: 너. 스포크: ① 기능 비교 ② 가격·라이선스 ③ 커뮤니티·업데이트 이력
각 스포크는 최종 답변에 1페이지 요약과 출처 링크를 담아 허브에게만 보고.
허브는 요약만 받아 비교표와 "우리가 따라야 할 3가지"를 작성.
```

**내부에서 일어나는 일**: 허브가 작업 목록과 의존 관계를 만들고, 스포크는 병렬로 일합니다. ②의 결과가 ③에 필요하면 허브가 요약을 ③에게 **중계**합니다(스포크끼리 직접 대화 없음).

**주의**: 허브가 스포크의 전체 로그를 읽게 하면 컨텍스트가 넘칩니다. “요약과 파일 목록만”을 지시문에 넣으세요.

## 예시 6. 엄격한 합격 기준이 있는 수정 (`delegate` + `delegation-eval-loop`)

**언제**: “됐다”는 말이 아니라 **증거**가 필요한 코드 수정.

```text
@skill:delegate @skill:delegation-eval-loop
checkout 금액 반올림 버그를 고쳐줘.
- 허용 경로: src/checkout/**, tests/checkout/**  (그 외 수정 금지)
- 합격 기준
  - [ ] pnpm test checkout 이 통과
  - [ ] 버그를 재현하는 회귀 테스트 추가
  - [ ] 관련 없는 파일 변경 없음
- 최종 답변에 실행한 명령과 원본 출력을 붙일 것
```

**내부에서 일어나는 일**

1. 부모가 계약(목표·허용 경로·체크리스트)을 지시문에 담아 자식에게 전달
2. 자식 완료 후 부모가 **직접** 테스트를 돌리고 `git diff --stat`으로 범위를 확인
3. 실패하면 오류 로그를 그대로 붙여 재지시(3~5회 한도), 통과해야 사용자에게 보고

**주의**: 자식의 “테스트 통과했습니다”는 증거가 아닙니다. 중단·취소된 실행이나 증거 없는 “완료”는 실패로 처리됩니다.

## 예시 7. 오래 가는 팀 만들기 (`teamwork` → `org`)

**언제**: 몇 주에 걸쳐 같은 팀이 이어서 일하고, 한곳에서 상태를 보고 싶을 때.

```text
@skill:teamwork
"월간 시장 동향 리포트" 태스크포스를 만들어줘.
역할: 리서처, 데이터 분석가, 에디터. 조율 방식은 허브–스포크.
산출물은 매월 reports/YYYY-MM.md, 에디터가 최종 승인.
```

준비가 끝나면 이어서:

```text
@skill:org
방금 준비한 팀으로 Org를 만들고 리서처부터 시작시켜줘.
```

**내부에서 일어나는 일**

1. `teamwork`가 미션·역할·조율 규칙을 앱 전용 폴더에 정리
2. `org`가 루트 세션에서 Org를 한 번 생성하고 멤버를 Org 소속으로 생성
3. 사이드바 **Org**에 팀이 나타나며, 다음 달에는 **Org 루트**에서 이어서 진행

이후 다듬기:

```text
@skill:org-restructure
데이터 분석가를 리서처에 합치고, 에디터 승인 기준을 ROLES.md 에 추가해줘.
```

**주의**: 일회성 위임은 Org에 나타나지 않습니다. 반복 실행이 목적이면 Org가 아니라 [예약 작업](scheduled-tasks.md)을 쓰세요. 팀을 다른 PC로 옮기려면 Org 화면의 **Export Org / Import Org**를 사용합니다.

## 예시 8. 기다려야 하는 일 (`call-me-back` / `loop`)

위임이 아니라 **깨우기**가 필요한 경우입니다.

```text
@skill:call-me-back
전체 빌드를 백그라운드로 돌리고, 끝나면 이 세션을 깨워서 실패한 테스트를 정리해줘.
```

```text
@skill:loop
30분 뒤에 이 PR의 CI 상태를 다시 확인해줘.
```

- 프로세스·웹훅 **완료**를 기다린다 → `call-me-back`
- **시간**이 지나면 다시 본다 → `loop` (이 대화 안), 앱을 닫아도 돌아야 하면 `schedule`

## 흔한 실수와 해결

| 증상                            | 원인                   | 해결                                                        |
| ------------------------------- | ---------------------- | ----------------------------------------------------------- |
| 자식이 파일·규칙·스킬을 못 찾음 | 작업 폴더가 격리됨     | “현재 작업 폴더 공유”를 명시하거나 내용을 지시문에 포함     |
| 부모가 자식 결과를 읽지 못함    | 자식이 파일에만 저장   | 산출물을 **최종 답변 본문**에 담도록 요구                   |
| 병렬 자식이 서로 파일을 덮어씀  | 같은 경로 공유         | 자식별 파일명·하위 폴더 분리                                |
| 자식이 계속 새로 생김           | 재사용 없이 매번 생성  | 쉬는 중인 같은 역할의 자식에게 `reset` 후 재배정하도록 요청 |
| “위임이 거절됨(깊이/팬아웃)”    | 계보 한도 초과         | 불필요한 하위 위임을 줄이거나 구조를 평탄화                 |
| 병렬이 느림                     | 활성 세션 한도(기본 4) | 묶음 크기를 줄이거나 단계로 나눔                            |
| 끝없는 리뷰 루프                | 기준이 모호            | 체크박스 합격 기준과 최대 재작업 횟수(기본 3) 지정          |
| 일회성 위임이 Org에 안 보임     | 정상 동작              | Org가 필요하면 `teamwork` → `org`                           |

더 많은 진단은 [문제 해결](troubleshooting.md)을 보세요.
