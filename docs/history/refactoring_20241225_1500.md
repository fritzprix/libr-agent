# Agentic Workflow Backend Migration Plan (Additive Strategy)

**Date:** 2024-12-25  
**Objective:** Migrate Agentic Workflow orchestration from React Frontend to Rust Backend using a "Dual-Track" additive strategy to ensure zero regression for existing features.

---

## 1. 작업의 목적 (Purpose)

**Primary Goal:**

- Decouple Agentic Workflow execution from React component lifecycle to prevent interruptions during session switching.
- Enable background execution of multiple concurrent agents independent of UI state.
- **Constraint:** Do not break or modify the existing `ChatContext` logic (Legacy Track).

**Secondary Goals:**

- Establish Rust as the single source of truth for session/message data (SQLite).
- Create a scalable architecture for future multi-agent collaboration features.

---

## 2. 현재의 상태 / 문제점 (Current State & Problems)

### Problem Identification

1. **Session Switching Interruption:**
   - `ChatContext.tsx` manages agentic flow state tied to the active session.
   - When user switches sessions, the previous session's React context unmounts.
   - Tool call loops and streaming states are lost, leading to incomplete workflows.

2. **State Fragmentation:**
   - Message history stored in IndexedDB (Frontend).
   - Session metadata managed by `session.rs` (Backend) but only file paths.
   - No coordination between the two → Risk of data inconsistency.

3. **Tool Call Management:**
   - Tool execution logic embedded in `ChatContext.tsx` and `useToolProcessor.ts`.
   - Cannot run tools if the component is unmounted.

### Current Architecture (Simplified)

```
User -> ChatInput -> ChatContext (React) -> useAIService (Hook)
                       ↓
                   useToolProcessor -> BuiltInToolProvider / External MCP
                       ↓
                   SessionHistoryContext -> IndexedDB
```

**Key Files:**

- `src/context/ChatContext.tsx`: Orchestrates message flow, tool execution, streaming.
- `src/hooks/use-ai-service.ts`: LLM provider integration, streaming.
- `src/context/SessionContext.tsx`: Session CRUD via IndexedDB.
- `src-tauri/src/session.rs`: File system workspace management.

**Data Flow (Current - ALREADY USING RUST SQLITE):**

- ❌ **NOT used for chat messages** (already in Rust SQLite)
- ✅ **ONLY used by Web MCP modules**: `planning-server`, `knowledge-server` for their internal state.

**Problem:** All of this orchestration logic still lives in React hooks tied to the component tree.

## 4. 변경 이후의 상태 / 해결 판정 기준 (Target State & Success Criteria)

### Target Architecture: Dual-Track Hybrid

We adopt a **"Dual-Track"** model to ensure 100% stability for existing features while introducing the new Rust-based orchestration.

- **Track 1 (Legacy)**: Existing `ChatContext` + `useAIService` (Frontend Orchestration). Used for existing sessions.
- **Track 2 (Agent V2)**: New `AgentSessionContext` + `AgentSessionManager` (Rust Orchestration). Used for new Agent sessions.

```
User -> ChatInput -> AgentSessionContext (TS)
                       ↓ (Tauri Command)
                   AgentSessionManager (Rust)
                       ↓
                   SQLite (Message History)
                       ↓
                   Agent Loop (Rust)
                       ↓
                   MCPServiceProxy (Rust) <-> Tool Execution (TS/Rust)
                       ↑
                   Tauri Event Emitter -> UI Update
```

**Key Changes:**

1. **Rust Owns Orchestration (V2 Only):** `AgentSessionManager` runs the tool call loop.
2. **Global TS Service:** `LLMServiceProviderContext` handles LLM streaming (multi-session support).
3. **Parallel Contexts:** `AgentSessionContext` exists alongside `ChatContext`.
4. **Reverse Tool Bridge:** Rust can request Web Tool execution from TS via IPC.

### Success Criteria

- [ ] Session switching does NOT interrupt running agents (V2).
- [ ] Multiple agents can run concurrently (tracked via session status).
- [ ] UI displays real-time status (Busy/Idle) for all sessions.
- [ ] Existing chat sessions (V1) continue to work exactly as before.

## 5. 수정이 필요한 코드 및 수정부분 (Code Changes)

### Detailed Technical Specifications (New)

#### 1. LLM Provider Integration Architecture

- **Initiator**: Rust (`AgentSessionManager`) initiates the call when it determines an LLM response is needed.
- **Protocol**:
  1.  Rust emits `llm:request` event with `{ requestId, messages, config }`.
  2.  TS (`LLMServiceProvider`) listens, calls `useAIService`.
  3.  TS streams chunks to UI (local state) for immediate feedback.
  4.  TS sends final complete message back to Rust via `agent_llm_response` command.
- **Configuration**: Rust stores the `AgentConfig` (model, temperature) in the Session DB. This config is passed in the `llm:request` payload.
- **Context Management**: TS (`useAIService`) continues to handle token counting and context pruning for now ("Wrap First"). Rust sends the full relevant history window (e.g., last 50 messages), and TS prunes it to fit the model's context window.

#### 2. Tool Execution Bridge Design

- **Discovery**: On session start, TS sends a list of available Web MCP tools to Rust via `register_web_tools` command. Rust stores this in the active session state.
- **Execution Flow**:
  - **Native Tools**: Rust executes directly via `rmcp`.
  - **Web Tools**: Rust emits `tool:request` -> TS executes -> TS calls `agent_tool_response`.
- **Built-in Tools**:
  - `SecureFileManager`: Already Rust-native.
  - `Browser`: Remains in TS (Web MCP) for now due to DOM dependency.
  - `Planning`: Remains in TS (Web MCP) for now.

#### 3. Migration Strategy (Additive)

- **Backward Compatibility**: Introduce a `use_v2_agent` boolean flag in the `Session` struct (default `false` for old sessions, `true` for new ones).
- **Schema Changes**: Add `status` column to `sessions` table (`idle`, `busy`, `paused`, `error`).
- **Coexistence**: The UI will check `use_v2_agent`.
  - If `true`: Render `AgentChatView` (uses `AgentSessionContext`).
  - If `false`: Render `ChatView` (uses `ChatContext`).

#### 4. Error Handling & Recovery

- **Crash Recovery**: If the app crashes, the Rust `AgentSessionManager` state is lost. On restart, any session with `status='busy'` in DB is reset to `status='paused'` or `idle`.
- **Workflow State**: For MVP, workflow state (e.g., "waiting for tool X") is in-memory. If the app closes, the workflow is interrupted. (This aligns with "Window stays open" constraint). Future versions can persist the state machine to DB.

#### A. Global LLM Service Context

**File:** `src/context/LLMServiceContext.tsx` (NEW)

```typescript
interface LLMServiceContextValue {
  // Multi-session support
  streamingMessages: Map<string, Partial<Message>>;

  // Invoked by Rust via IPC
  executeCompletionRequest: (
    sessionId: string,
    messages: Message[],
    config: AIServiceConfig,
  ) => Promise<Message>;

  // Status tracking
  getSessionStatus: (sessionId: string) => 'idle' | 'streaming' | 'error';
}

export function LLMServiceProvider({ children }: { children: ReactNode }) {
  const [streamingMessages, setStreamingMessages] = useState<
    Map<string, Partial<Message>>
  >(new Map());

  // Listen for Rust commands
  useEffect(() => {
    const unlisten = listen<CompletionRequest>(
      'llm:completion-request',
      async (event) => {
        const { sessionId, messages, config } = event.payload;
        const result = await performCompletion(sessionId, messages, config);

        // Send result back to Rust
        await invoke('report_completion', { sessionId, message: result });
      },
    );

    return () => {
      unlisten.then((fn) => fn());
    };
  }, []);

  // ... implementation
}
```

**Key Points:**

- This provider lives at the `<App>` level, never unmounts.
- Uses `useAIService` internally but wraps it in a session-aware manner.
- Throttles UI updates (e.g., update every 50ms) to reduce render load.

```typescript
export function ToolBridgeProvider({ children }: { children: ReactNode }) {
  useEffect(() => {
    const unlisten = listen<ToolExecutionRequest>('tool:execute-request', async (event) => {
      const { toolName, params, sessionId } = event.payload;

      // Route to appropriate handler
      let result: ToolResult;
      if (toolName.startsWith('builtin_')) {
        result = await executeBuiltInTool(toolName, params);
      } else {
        result = await executeWebMCPTool(toolName, params);
      }

      // Send result back to Rust
      await invoke('report_tool_result', { sessionId, result });
    });

    return () => { unlisten.then(fn => fn()); };
  }, []);

  return <>{children}</>;
}
```

```typescript
export function useAgentStatus(sessionId: string) {
  const [status, setStatus] = useState<'idle' | 'busy' | 'error'>('idle');

  useEffect(() => {
    const unlisten = listen<AgentEvent>('agent:event', (event) => {
      if (event.payload.session_id === sessionId) {
        setStatus(event.payload.status);
      }
    });

    return () => {
      unlisten.then((fn) => fn());
    };
  }, [sessionId]);

  return status;
}
```

## 9. Clarification Q-List (Unresolved Questions)

### Q1: IndexedDB Migration Strategy [RESOLVED]

**Context:** The project **already uses SQLite in Rust backend** (`src-tauri/src/repositories/`).

**Status:** ✅ **SQLite infrastructure is production-ready.**

- `MessageRepository`, `SessionRepository`, `ContentStoreRepository` are fully implemented.
- Global state management via `state.rs` with `OnceLock` pattern.
- Existing schema includes all necessary fields (id, session_id, role, content, tool_calls, etc.).

**New Question:** Is the **Frontend currently using IndexedDB or already calling Rust SQLite**?

- **Action Required:** Verify `SessionContext.tsx` and `SessionHistoryContext.tsx` to determine current data flow.
- If IndexedDB is still in use, we need a gradual migration strategy (Option B from original question).

### Q2: Session Status Persistence

**Question:** Should session status (busy/idle/error) be persisted in SQLite or kept as in-memory state in Rust?

- **Option A:** Persist to DB (survives app restart, but more writes).
- **Option B:** In-memory only (simpler, but lost on restart).

**Recommendation:** In-memory for MVP, persist later if needed.

### Q3: Tool Call Timeout Handling

**Question:** What happens if a tool call takes too long (e.g., user-initiated file search in a large directory)?

- Should the agent "pause" and wait indefinitely?
- Should there be a configurable timeout?
- Should the UI show a "Tool XYZ is taking longer than expected" message?

**Recommendation:** Implement 60s default timeout with UI notification.

### Q4: Error Recovery Strategy

**Question:** If the LLM returns an empty response or rate limit error mid-workflow, should the agent:

- Retry automatically (with exponential backoff)?
- Pause and notify the user?
- Cancel the workflow?

**Recommendation:** Retry 3 times, then pause with notification.
