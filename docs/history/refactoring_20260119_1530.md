# Refactoring Plan: Fix Duplicate MCP Tools & Global Manager Role Clarification

## 1. 작업 목적 (Purpose)

- **MCP 도구 중복 제거**: 현재 Stdio 기반의 외부 MCP 서버 도구가 AI 에이전트에게 2중으로(Global + Session) 노출되어 발생하는 오류("Duplicate function declaration") 수정.
- **세션 격리 강화**: Stdio 서버는 반드시 세션별로 격리된 프로세스(`SessionMCPManager`)를 통해서만 관리되도록 강제하고, Global Manager가 이에 개입하지 않도록 수정.
- **Global Manager의 역할 명확화**: Global Manager가 필요한 이유를 명확히 하고, Stdio 관리 기능의 이관 여부를 결정.

## 2. 현재 상태 / 문제점 (Current Status / Problems)

### 2.1 아키텍처 충돌

현재 코드는 Stdio MCP 서버를 두 곳에서 관리하고 있습니다:

1. **Global `MCPServerManager`**: "상태 확인" 기능이나 `list_tools_from_config` 실행 시 Stdio 프로세스를 Global Connection으로 등록함.
2. **Session `SessionMCPManager`**: 세션 생성 시(`create_proxy`) `eager tool discovery`를 통해 세션 전용 프로세스를 생성하고 도구를 등록함.

### 2.2 중복 도구 발생 경로

`src-tauri/src/agent/tools.rs`의 `collect_available_tools` 함수에서 도구를 수집할 때:

1. `proxy_manager.list_all_external_tools()`를 호출하여 Global Manager의 도구를 가져옴 (여기서 Stdio 도구가 1차로 포함됨).
2. `proxy.get_session_stdio_tools()`를 호출하여 Session Manager의 도구를 가져옴 (여기서 Stdio 도구가 2차로 포함됨).
3. 결과적으로 동일한 도구가 2개씩 존재하게 되어 LLM 호출 시 스키마 중복 에러 발생.

### 2.3 Global Manager의 역할 분석

**Global MCPServerManager가 필요한 이유:**

1. **Frontend UI 상태 확인**: `MCPServerContext`에서 `listToolsFromConfig` → `list_tools_from_config` 호출 시 설정된 모든 서버(HTTP + Stdio)의 도구 목록을 UI에 표시하기 위함.
   - 위치: `src/context/MCPServerContext.tsx`의 `connectServers` 함수
   - 목적: 사용자에게 "어떤 도구들이 사용 가능한지" 미리 확인시켜 주는 용도

2. **HTTP 서버 관리**: HTTP 기반 MCP 서버는 여러 세션에서 공유 가능하므로 Global Manager에서 관리하는 것이 효율적.

3. **Agent V2의 도구 수집**: `collect_available_tools`에서 `list_all_external_tools` 호출 시 Global Manager의 연결 목록을 조회하여 사용.

**문제점:**

- `list_tools_from_config`는 **설정 검증 목적**으로 Stdio 서버를 임시로 시작하지만, 이 연결이 Global `connections` HashMap에 영구적으로 남아있음.
- 이후 Agent 세션이 시작될 때 **같은 Stdio 서버가 Session Manager에서도 독립적으로 시작**되어 중복 발생.
- Global Manager의 `list_all_tools`는 `connections`의 모든 항목(HTTP + Stdio)을 반환하므로, Stdio 도구가 2번 수집됨.

## 3. 변경 이후의 상태 (Target State)

- **Global Manager**: HTTP 기반의 공유 MCP 서버만 관리. `list_all_tools` 호출 시 Stdio 서버는 배제함.
- **Session Manager**: Stdio 기반의 격리된 MCP 서버만 관리.
- **Frontend**: "상태 확인" 등으로 인해 Global Manager에 Stdio 연결이 임시로 생기더라도, Agent 도구 수집 단계에서는 무시됨.

## 4. 수정이 필요한 코드 및 구현 가이드 (Implementation Guide)

### 4.1 `src-tauri/src/mcp/server/tools.rs` 수정 ✅ (완료)

Global Manager가 관리하는 연결(`connections`) 중에서 **Stdio 타입은 필터링하고 HTTP 타입만 반환**하도록 `list_all_tools` 함수를 수정합니다.

```rust
// src-tauri/src/mcp/server/tools.rs

use crate::mcp::types::TransportConfig; // Import 추가 필요

pub async fn list_all_tools(manager: &MCPServerManager) -> Result<Vec<MCPTool>> {
    let mut all_tools = Vec::new();

    // Server names 수집 단계에서 TransportConfig::Http 인 것만 필터링
    let server_names: Vec<String> = {
        let connections = manager.connections.lock().await;
        connections.iter()
            .filter(|(_, conn)| {
                // ✅ FIX: Stdio 서버는 Global 리스트에서 제외 (SessionManager가 담당)
                matches!(conn.config.transport, TransportConfig::Http { .. })
            })
            .map(|(name, _)| name.clone())
            .collect()
    };

    for server_name in server_names {
        match list_tools(manager, &server_name).await {
            Ok(mut tools) => {
                // Prefix logic 유지
                for tool in &mut tools {
                    tool.name = format!("{}__{}", server_name, tool.name);
                }
                all_tools.extend(tools);
            }
            Err(e) => {
                warn!("Failed to get tools from server {server_name}: {e}");
            }
        }
    }

    Ok(all_tools)
}
```

### 4.2 `src-tauri/src/commands/mcp_commands.rs` (Optional / Future Work)

현재 `list_tools_from_config`는 설정 검증을 위해 `manager.start_server`를 호출하여 부작용(Global state에 Stdio process 생성)을 일으킵니다.

**단기 해결책 (이번 리팩토링):**

- 4.1의 필터링으로 중복 노출을 막는 것을 우선으로 함.
- `list_tools_from_config`는 UI에서 설정 검증 목적으로 계속 사용됨.

**장기 해결책 (향후 과제):**

- `list_tools_from_config`가 Stdio 서버를 시작한 후 **임시로만 사용하고 즉시 `stop_server`를 호출**하도록 수정.
- 또는 설정 검증용 별도의 경량 API를 만들어 Global state에 영구적인 연결을 남기지 않도록 개선.

### 4.3 Global Manager의 역할 명확화

**Global MCPServerManager를 제거하지 않는 이유:**

1. **UI 상태 확인 기능**: Frontend에서 `listToolsFromConfig`를 통해 설정된 서버들의 도구 목록을 미리 확인할 필요가 있음.
2. **HTTP 서버 공유**: 여러 세션에서 공유 가능한 HTTP 기반 MCP 서버는 Global Manager에서 관리하는 것이 효율적.
3. **기존 API 호환성**: `list_all_external_tools`, `getConnectedServers` 등 Frontend에서 사용 중인 API들이 Global Manager에 의존.

**따라서 이번 리팩토링의 범위:**

- Global Manager의 **Stdio 관리 기능 자체를 제거하는 것이 아님**.
- Global Manager가 **Agent 도구 수집 시 Stdio 도구를 노출하지 않도록 필터링**하는 것.
- Session Manager의 Stdio 도구만 Agent에게 제공되도록 보장.

## 5. 해결 판정 기준 (Acceptance Criteria)

1. **중복 제거 확인**: Agent Session에서 Stdio MCP 서버(예: `rpg-mcp-server`)를 사용할 때, `collect_available_tools` 결과에 해당 도구가 **단 한 번만** 등장해야 함.
2. **기능 유지 확인**:
   - HTTP 기반 MCP 서버는 여전히 Global Manager를 통해 정상적으로 검색되어야 함.
   - Session-isolated Stdio 서버는 Session Manager를 통해 정상적으로 검색되어야 함.
   - Frontend의 "상태 확인" 기능은 정상 작동해야 함 (UI에는 모든 도구가 표시되지만, Agent에는 필터링됨).

## 8. Clarification Q-list

### Q1: `list_tools_from_config`의 장기 개선 전략

**현재 상태:**

- UI에서 "상태 확인" 버튼 클릭 시 모든 서버(HTTP + Stdio)를 Global Manager에 연결함.
- 이 연결들이 영구적으로 남아있어 Agent 세션 시작 시 중복 발생.

**고려 사항:**

1. `list_tools_from_config` 실행 후 Stdio 서버를 즉시 `stop_server`로 정리할 것인가?
   - 장점: Global state 오염 방지
   - 단점: UI에서 재확인 시 매번 프로세스 재시작 필요 (성능 저하)

2. 설정 검증용 별도 API를 만들어 임시 연결로만 처리할 것인가?
   - 장점: 깔끔한 아키텍처 분리
   - 단점: 추가 개발 비용

**권장 사항:**

- 이번 리팩토링에서는 4.1의 필터링으로 중복 문제 해결.
- 향후 성능 개선이 필요할 때 Q1의 전략 중 하나를 선택하여 적용.
