# Refactoring Plan: MCP Server Type Consolidation

## 작업의 목적

MCPServer 관련 타입 정의의 중복을 제거하고, 프로젝트 전체에서 일관된 타입 체계를 구축하여 코드의 가독성과 유지보수성을 향상시킵니다.

### 목표

- 중복되고 deprecated된 타입 정의 제거
- V2 suffix 제거하여 명확한 네이밍 체계 확립
- Frontend와 Backend 간 타입 일관성 유지
- Legacy 설정 파일 지원을 위한 최소한의 호환 레이어 유지

## 현재의 상태 / 문제점

### 타입 중복 및 분산 문제

현재 프로젝트에는 MCPServer 관련 타입이 여러 파일에 걸쳐 중복 정의되어 있습니다:

#### Frontend TypeScript

1. **`MCPServerConfigV2`** (`src/lib/mcp/config/server-config.ts`)
   - MCP 2025-06-18 스펙을 따르는 최신 설정 포맷
   - `transport: TransportConfig`, `authentication?`, `metadata?` 포함
   - **현재 사용 중**: 11개 파일에서 참조

2. **`LegacyMCPServerConfig`** (`src/lib/mcp/config/server-config.ts`)
   - 구버전 stdio 전용 단순 설정 포맷
   - `command`, `args`, `env`만 포함
   - **현재 사용 중**: 6개 파일에서 참조 (주로 타입 가드 및 변환 함수)

3. **`MCPServerConfig`** (Deprecated) (`src/lib/mcp/config/server-config.ts`)
   - 초기 버전의 설정 타입
   - `transport: 'stdio' | 'http' | 'websocket'` (문자열)
   - **사용 안 됨**: 정의만 존재, 실제 사용처 없음

4. **`MCPServerConfig`** (재정의) (`src/hooks/use-rust-backend.ts`)
   - 불필요한 재정의 (backward compatibility 목적이라고 명시)
   - `name`, `transport: string`, `[key: string]: unknown`
   - **문제**: 원본 타입과 이름은 같지만 구조가 다름

5. **`UnifiedMCPServerConfig`** (`src/lib/mcp/config/server-config.ts`)
   - Tauri/WebWorker 통합 설정을 위한 타입
   - `type: 'tauri' | 'webworker'` 필드 포함
   - **사용 안 됨**: 정의만 존재, 실제 사용처 없음

6. **`MCPToolExecutionContext`** (`src/lib/mcp/config/server-config.ts`)
   - Tool 실행 컨텍스트 정의
   - **사용 안 됨**: 정의만 존재, 실제 사용처 없음

7. **`MCPServerEntity`** (`src/models/chat.ts`)
   - **핵심 타입**: 앱 전체에서 사용되는 메인 엔티티
   - DB 메타데이터 (`id`, `isActive`, `createdAt`, `updatedAt`) 포함
   - MCP 설정 필드 (`name`, `transport`, `authentication`, `metadata`) 포함
   - **현재 사용 중**: 102개 참조 (가장 많이 사용됨)

#### Backend Rust

1. **`MCPServerConfigV2`** (`src-tauri/src/mcp/types.rs`)
   - Frontend의 `MCPServerConfigV2`와 동일한 구조
   - Serde로 직렬화/역직렬화

2. **`MCPServerConfig`** (Legacy) (`src-tauri/src/mcp/types.rs`)
   - Frontend의 deprecated `MCPServerConfig`와 유사
   - Legacy 포맷 지원용

3. **`MCPServerConfigWrapper`** (`src-tauri/src/mcp/types.rs`)
   - V2와 Legacy를 자동 감지하고 변환하는 enum
   - **현재 사용 중**: `list_tools_from_config` 등에서 설정 파싱 시 사용

### 구조적 문제점

1. **네이밍 불일치**
   - 최신 타입에 `V2` suffix가 붙어 있어 버전이 변경될 때마다 전체 리팩토링 필요
   - 동일한 이름(`MCPServerConfig`)이 여러 의미로 사용됨

2. **타입 계층 불명확**
   - 설정 타입(`Config`)과 엔티티 타입(`Entity`)의 관계가 명확하지 않음
   - 변환 함수와 타입 가드가 산재되어 있음

3. **미사용 타입**
   - `UnifiedMCPServerConfig`, `MCPToolExecutionContext` 등 정의만 있고 사용하지 않는 타입
   - 코드베이스를 복잡하게 만들고 혼란 초래

4. **중복 정의**
   - `use-rust-backend.ts`의 불필요한 타입 재정의
   - Frontend/Backend 간 동일 구조 타입의 중복 유지 (필요하지만 네이밍은 일치해야 함)

#### 3. Backend 서버 시작 (Rust)

```rust
// lifecycle.rs
pub async fn start_server_v2(
    manager: &MCPServerManager,
    config: MCPServerConfigV2,
) -> Result<String> {
    match &config.transport {
        TransportConfig::Stdio { command, args, env } => {
            let legacy_config = MCPServerConfig { /* convert */ };
            start_stdio_server(manager, legacy_config).await
        }
        TransportConfig::Http { url, .. } => {
            start_http_server(manager, config.name, url, ..).await
        }
    }
}
```

### 핵심 패턴 분석

1. **MCPServerEntity는 앱 상태의 중심**
   - UI, DB, Context 모두 이 타입 사용
   - DB 메타데이터와 MCP 설정을 함께 포함

2. **MCPServerConfigV2는 Backend 통신 인터페이스**
   - Tauri command 호출 시 사용
   - Rust와 TypeScript 간 직렬화/역직렬화 경계

3. **Backend는 Wrapper로 유연성 확보**
   - 설정 파일이 Legacy든 V2든 자동 감지
   - 내부적으로 V2로 변환하여 처리

4. **Legacy 지원은 필수**
   - 기존 사용자 설정 파일 호환성
   - stdio 전용 간단한 설정 지원

```typescript
/**
 * MCP Server Configuration (MCP 2025-06-18 Spec Compliant)
 */
export interface MCPServerConfig {
  name: string;
  transport: TransportConfig;
  authentication?: OAuthConfig;
  metadata?: ServerMetadata;
}

/**
 * Legacy MCP Server Configuration (stdio-only, for backward compatibility)
 * @internal Used only for config file parsing
 */
export interface LegacyMCPServerConfig {
  command: string;
  args?: string[];
  env?: Record<string, string>;
}

/**
 * Top-level MCP configuration supporting both modern and legacy formats
 */
export interface MCPConfig {
  mcpServers?: Record<string, MCPServerConfig | LegacyMCPServerConfig>;
}

/**
 * Type guard to check if config is modern format
 */
export function isModernConfig(
  config: MCPServerConfig | LegacyMCPServerConfig,
): config is MCPServerConfig {
  return 'transport' in config && typeof config.transport === 'object';
}

/**
 * Convert legacy config to modern format
 */
export function convertLegacyToModern(
  name: string,
  legacy: LegacyMCPServerConfig,
): MCPServerConfig {
  return {
    name,
    transport: {
      type: 'stdio',
      command: legacy.command,
      args: legacy.args,
      env: legacy.env,
    },
  };
}
```

```typescript
/**
 * Type guard to check if config is modern format
 */
export function isModernConfig(
  config: MCPServerConfig | LegacyMCPServerConfig,
): config is MCPServerConfig {
  return 'transport' in config && typeof config.transport === 'object';
}

/**
 * Normalize config to modern format
 */
export function normalizeConfig(
  name: string,
  config: MCPServerConfig | LegacyMCPServerConfig,
): MCPServerConfig {
  if (isModernConfig(config)) {
    return config;

  return convertLegacyToModern(name, config);
```

## Clarification Q-list (검토 및 의사 결정 필요 사항)

### 1. Legacy Support 범위

**Q**: `LegacyMCPServerConfig`를 완전히 제거할 것인가, 아니면 내부적으로 유지할 것인가?

**Options**:

- A) 완전 제거: 사용자에게 설정 파일 업데이트 요구 (Breaking Change)
- B) 내부 유지: Wrapper를 통해 자동 변환 (현재 전략)
- C) Deprecation 경고: 현재는 동작하지만 미래 버전에서 제거 예고

**Recommendation**: Option B (내부 유지)를 권장합니다. 기존 사용자의 설정 파일 호환성을 보장하고, 자동 마이그레이션으로 부드러운 전환을 제공합니다.

### 2. MCPServerEntity 구조 개선

**Q**: `MCPServerEntity`가 `MCPServerConfig`의 모든 필드를 중복으로 포함하고 있습니다. 상속 또는 composition 패턴을 사용할 것인가?

**Options**:

- A) 현재 구조 유지: 명시적이지만 중복이 있음

  ```typescript
  export interface MCPServerEntity {
    id: string;
    isActive: boolean;
    createdAt: Date;
    updatedAt: Date;
    name: string;
    transport: TransportConfig;
    // ...
  }
  ```

- B) Composition 패턴:

  ```typescript
  export interface MCPServerEntity {
    id: string;
    isActive: boolean;
    createdAt: Date;
    updatedAt: Date;
    config: MCPServerConfig;
  }
  ```

- C) Intersection 타입:

  ```typescript
  export interface MCPServerMetadata {
    id: string;
    isActive: boolean;
    createdAt: Date;
    updatedAt: Date;
  }

  export type MCPServerEntity = MCPServerMetadata & MCPServerConfig;
  ```

**Recommendation**: Option A (현재 구조 유지)를 권장합니다. DB 스키마와 일대일 매핑이 명확하고, 이미 102개 파일에서 사용 중이므로 변경 비용이 높습니다. 향후 별도 refactoring으로 분리 가능합니다.

### 3. 네이밍 컨벤션

**Q**: Legacy 타입을 `LegacyMCPServerConfig`로 할 것인가, 아니면 다른 이름을 사용할 것인가?

**Options**:

- A) `LegacyMCPServerConfig`: 명확하지만 길다
- B) `SimpleMCPServerConfig`: 의미 중심 네이밍
- C) `StdioMCPServerConfig`: 용도 중심 네이밍

**Recommendation**: Option A (`LegacyMCPServerConfig`)를 권장합니다. "Legacy"라는 단어가 향후 제거될 수 있음을 명확히 나타내고, 기존 코드베이스에서 이미 사용 중입니다.

### 4. V2 Suffix 제거 타이밍

**Q**: 이번 리팩토링에서 즉시 V2 suffix를 제거할 것인가, 아니면 단계적으로 진행할 것인가?

**Options**:

- A) 즉시 제거: 한 번의 큰 변경으로 처리
- B) 단계적 제거:
  1. Phase 1: `MCPServerConfig` 추가 (alias)
  2. Phase 2: 사용처를 서서히 마이그레이션
  3. Phase 3: `MCPServerConfigV2` deprecated 경고
  4. Phase 4: 완전 제거

**Recommendation**: Option A (즉시 제거)를 권장합니다. 프로젝트가 아직 초기 단계(dev/0.4.0)이고, 단일 PR로 변경을 완료하는 것이 추적 관리에 유리합니다.

### 5. Rust의 Legacy Type 가시성

**Q**: Rust의 `LegacyMCPServerConfig`를 public으로 유지할 것인가?

**Options**:

- A) Public: Frontend에서 직접 접근 가능
- B) Crate-private (`pub(crate)`): 내부에서만 사용
- C) Module-private (private): `types` 모듈 내부에서만 사용

**Recommendation**: Option B (`pub(crate)`)를 권장합니다. 다른 Rust 모듈에서는 접근 가능하지만 Frontend에는 노출되지 않아 안전합니다.

### 6. 마이그레이션 도구 제공 여부

**Q**: 사용자 설정 파일을 자동으로 Modern 포맷으로 변환하는 CLI 도구를 제공할 것인가?

**Options**:

- A) 제공: `pnpm migrate-config` 등의 스크립트
- B) 미제공: 런타임 자동 변환에만 의존

**Recommendation**: Option B (미제공)를 권장합니다. Wrapper가 런타임에 자동으로 감지/변환하므로 별도 마이그레이션 불필요합니다. 필요 시 향후 추가 가능합니다.

### 7. Breaking Change 처리

**Q**: 이 리팩토링을 Breaking Change로 간주하고 Major version bump를 할 것인가?

**Options**:

- A) Breaking Change: v0.5.0 또는 v1.0.0으로 bump
- B) Non-breaking: v0.4.1로 처리 (내부 리팩토링)

**Recommendation**: Option B (Non-breaking)를 권장합니다. Public API가 변경되지 않고 (Wrapper가 호환성 유지), 사용자 관점에서는 동일하게 동작합니다. 내부 타입 정리는 Minor version에 포함 가능합니다.
