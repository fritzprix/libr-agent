# Refactoring Plan: Agent Workflow In-Memory Message Stack Architecture

**Date**: 2024-12-28 23:30  
**Status**: Planning Phase  
**Priority**: High (Performance Critical)

---

## 🚀 요약 (신규 개발자를 위한 가이드)

### 1. 배경 및 문제점

현재 LibrAgent 백엔드는 **DB 중심 아키텍처(DB-Centric Architecture)**를 사용하고 있습니다. 에이전트가 "생각"하거나 도구를 실행할 때마다 시스템은 SQLite에서 전체 대화 기록(최대 1000개 메시지)을 다시 로드합니다.

- **버그**: 메시지 로딩의 "무한 루프"로 인해 성능 저하 및 UI 동기화 문제(도구 결과가 표시되지 않음)가 발생했습니다.
- **목표**: **하이브리드 인메모리 아키텍처(Hybrid In-Memory Architecture)**로 전환합니다. 활성 세션 메시지를 RAM에 유지하여 즉시 액세스하고, 비동기적으로 DB에 유지합니다.

### 2. 해결책: 하이브리드 인메모리 캐시

`AgentSession` 구조체를 수정하여 메시지를 메모리에 보유합니다:

- **읽기**: 메모리에서 `O(1)` 액세스. DB 쿼리 없음.
- **쓰기**: 메모리 즉시 업데이트 -> UI 이벤트 발행 -> 비동기 DB 저장.
- **메모리 안전성**: **슬라이딩 윈도우(Sliding Window)**(최대 1000개 메시지)를 사용하여 RAM 팽창 방지. **RAII**를 사용하여 세션 자동 정리.

## 📚 용어 사전

- **AgentSession**: 활성 채팅 세션을 나타내는 Rust 구조체. 현재는 상태가 없지만(자주 재생성됨), 상태를 가지게 됩니다(메모리에 장기 생존).
- **Sliding Window (슬라이딩 윈도우)**: 가장 최근 N개(예: 1000개)의 메시지만 메모리에 유지하는 로직. 오래된 메시지는 DB에는 존재하지만 RAM에서는 제거됩니다.
- **RAII (Resource Acquisition Is Initialization)**: Rust 패턴으로, `Drop` 트레이트를 구현하여 세션이 스코프를 벗어나거나(`Arc` 카운트가 0이 될 때) 자동으로 저장/정리되도록 합니다.
- **Arc<RwLock<...>>**: 스레드 안전 스마트 포인터. `Arc`는 스레드 간(예: HTTP 서버와 백그라운드 워커) 소유권 공유를 허용하고, `RwLock`은 안전한 동시 액세스를 허용합니다.

## 작업의 목적

Agent Workflow에서 발생하는 두 가지 핵심 문제 해결:

1. **성능 병목 제거**: 매 submit마다 DB에서 1000개 메시지 로드하는 비효율 제거
2. **UI 동기화 개선**: Tool 실행 결과 메시지가 UI에 표시되지 않는 문제 해결

**예상 효과**:

- Submit 지연시간 95-98% 감소 (100-300ms → 1-5ms)
- Tool call 시 DB 쿼리 99% 감소 (매 tool마다 → 초기 1회만)
- UI와 LLM context의 일관성 보장

## 현재의 상태 / 문제점

### 문제 1: 순수 DB-Centric 아키텍처로 인한 성능 저하

**증상**:

- 사용자가 메시지를 보낼 때마다 `agent_service.rs:request_llm_completion()`에서 DB 쿼리 발생
- Tool call이 5개인 경우 총 6번의 DB 쿼리 (초기 1회 + tool 결과 처리마다 1회씩)
- 각 쿼리는 최대 1000개 메시지를 로드하고 JSON 역직렬화 수행

**근본 원인**:

```rust
// src-tauri/src/agent/types.rs:127-132
pub struct AgentSession {
    pub metadata: SessionMetadata,
    pub is_running: bool,
    pub cancellation_token: CancellationToken,
    pub pending_execution: Option<PendingToolExecution>,
    // ❌ messages: Vec<Message> 필드 없음
}
```

- `AgentSession`이 메시지를 메모리에 캐싱하지 않음
- 매번 DB에서 full load 필요

**성능 지표** (실측 필요):
| 시나리오 | DB 쿼리 | 메시지 로드 | 예상 지연시간 |
|----------|---------|-------------|---------------|
| 일반 채팅 | 1회 | 1000개 | 100-300ms |
| Tool 3개 | 4회 | 4000개 | 400-1200ms |
| 10턴 대화 | 10회 | 10,000개 | 1-3초 |

### 문제 2: MessageAdded 이벤트 미발행으로 UI 동기화 실패

**증상**:

- Tool 실행 결과 메시지가 UI에 표시되지 않음
- `AgentChatContext.tsx:240-256`에서 `MessageAdded` 이벤트를 리스닝하지만 이벤트가 발행되지 않음

**근본 원인**:

```rust

    // ...
    MessageAdded {
        session_id: String,
        message_id: String,  // 정의되어 있지만...
```

- `MessageAdded` enum variant는 정의되어 있음
- 하지만 `emit_event(AgentEvent::MessageAdded {...})` 호출이 코드베이스에 존재하지 않음 (grep 결과 0건)
- Tool 실행 결과 저장 후 이벤트 발행 로직 누락

## 관련 코드의 구조 및 동작 방식 Summary

### 현재 Message Flow Architecture

```
[Two Separate Paths]

PATH 1: LLM Request Flow (메시지 스택 전달)
┌──────────────────────────────────────────────────────────────┐
│ Frontend (AgentChatContext)                                  │
│   submit(userMessage)                                        │
│     → setLocalMessages([...prev, userMessage])  (Optimistic)│
│     → invoke('agent_send_message', { message })              │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────────┐
│ Rust Backend (agent_service.rs)                             │
│   start_workflow(session_id, user_message)                  │
│     → message_repo.insert(&user_message)  (DB 저장)         │
│     → request_llm_completion(session_id)                     │
│                                                               │
│   request_llm_completion(session_id)                         │
│     → page = message_repo.get_page(&session_id, 1, 1000) ❌  │
│     → messages = page.items  (1000개 로드)                   │
│     → emit("llm:completion-request", { messages, ... })      │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────────┐
│ Frontend (LLMServiceContext)                                 │
│   listen('llm:completion-request')                           │
│     → executeCompletionRequest(messages, ...)                │
│     → LLM API call with full message history                 │
└──────────────────────────────────────────────────────────────┘

PATH 2: UI Update Flow (화면 표시)
┌──────────────────────────────────────────────────────────────┐
│ Rust Backend (agent_service.rs)                             │
│   [Tool execution result saved]                              │
│   ❌ MessageAdded 이벤트 발행 누락                            │
└──────────────────────────────────────────────────────────────┘
                          ↓ (Should exist but doesn't)
┌──────────────────────────────────────────────────────────────┐
│ Frontend (AgentChatContext)                                  │
│   listen('agent:event')                                      │
│     → if (eventType === 'MessageAdded')                      │
│       → setLocalMessages([...prev, newMessage])              │
│         (Never triggered because event not emitted)          │
└──────────────────────────────────────────────────────────────┘
```

## 변경 이후의 상태 / 해결 판정 기준

### 목표 아키텍처: Hybrid Memory-DB Architecture

```
[Optimized Flow with In-Memory Cache]

Session Initialization (Resume)
┌──────────────────────────────────────────────────────────────┐
│ Rust Backend                                                 │
│   init_session_with_messages(session_id)                     │
│     → messages = message_repo.get_page(1, 1000)  ✅ 1회만     │
│     → session.messages = Arc::new(RwLock::new(messages))     │
└──────────────────────────────────────────────────────────────┘

Message Submission (Every Turn)
┌──────────────────────────────────────────────────────────────┐
│ Rust Backend                                                 │
│   start_workflow(user_message)                               │
│     1. session.messages.push(user_message)  ✅ 메모리 추가    │
│     2. tokio::spawn { message_repo.insert() }  ✅ 비동기 저장 │
│     3. request_llm_completion()                               │
│          → messages = session.messages.clone()  ✅ 메모리 읽기│
│          → emit("llm:completion-request", ...)                │
└──────────────────────────────────────────────────────────────┘

Tool Result Handling
┌──────────────────────────────────────────────────────────────┐
│ Rust Backend                                                 │
│   handle_tool_result(tool_messages)                          │
│     1. session.messages.extend(tool_messages)  ✅ 메모리 추가 │
│     2. tokio::spawn { bulk insert to DB }  ✅ 비동기 저장     │
│     3. emit(AgentEvent::MessageAdded { message })  ✅ UI 이벤트│
│     4. request_llm_completion()  ✅ DB 쿼리 없음              │
└──────────────────────────────────────────────────────────────┘

UI Update
┌──────────────────────────────────────────────────────────────┐
│ Frontend (AgentChatContext)                                  │
│   listen('agent:event')                                      │
│     → MessageAdded event received  ✅                         │
│     → setLocalMessages([...prev, message])  ✅ UI 업데이트    │
└──────────────────────────────────────────────────────────────┘
```

### 2. Session 초기화 메서드 추가

**파일**: `src-tauri/src/agent/agent_service.rs` (새 메서드)

```rust
/// Load messages from DB and populate in-memory cache
/// Called once during session resume or initialization
async fn init_session_with_messages(&self, session_id: &str) -> Result<(), String> {
    let message_repo = crate::state::get_message_repository();

    // Load all messages from DB (one-time operation)
    let page = message_repo
        .get_page(session_id, 1, 1000)
        .await
        .map_err(|e| format!("Failed to load messages: {}", e))?;

    let mut sessions = self.active_sessions.write().await;
    if let Some(session) = sessions.get_mut(session_id) {
        let mut messages = session.messages.write().await;
        *messages = page.items;

        let mut synced_at = session.last_synced_at.write().await;
        *synced_at = chrono::Utc::now().timestamp_millis();

        log::info!(
            "Loaded {} messages into session cache: {}",
            messages.len(),
            session_id
        );
    }

    Ok(())
}
```

**호출 위치**:

- `resume_agent_session` command
- 새 session 생성 시 (첫 메시지 전송 전)

```rust
// After
pub async fn start_workflow(
    &self,
    session_id: String,
    user_message: Message,
) -> Result<(), String> {
    self.update_session_status(&session_id, SessionStatus::Busy).await?;

    // 1. Add to in-memory cache first (immediate, non-blocking)
    {
        let sessions = self.active_sessions.read().await;
        let session = sessions
            .get(&session_id)
            .ok_or_else(|| format!("Session not found: {}", session_id))?;

        let mut messages = session.messages.write().await;
        messages.push(user_message.clone());
    }

    // 2. Persist to DB asynchronously (non-blocking)
    let message_for_db = user_message.clone();
    let session_id_clone = session_id.clone();
    tokio::spawn(async move {
        let message_repo = crate::state::get_message_repository();
        if let Err(e) = message_repo.insert(&message_for_db).await {
            log::error!(
                "Failed to save user message to DB: session={}, error={}",
                session_id_clone,
                e
            );
        }
    });

    // 3. Request LLM completion with in-memory messages
    self.request_llm_completion(session_id).await?;
    Ok(())
}
```

### 5. Tool 결과 처리 메서드 수정

**파일**: `src-tauri/src/agent/agent_service.rs` (tool result handling 위치 확인 필요)

```rust
// Before
pub async fn handle_tool_result(
    &self,
    session_id: String,
    accumulated_messages: Vec<Message>,
) -> Result<(), String> {
    let message_repo = crate::state::get_message_repository();

        message_repo.insert(&msg).await?;

    self.request_llm_completion(session_id).await?;
    Ok(())
}

// After
pub async fn handle_tool_result(
    &self,
    session_id: String,
    accumulated_messages: Vec<Message>,
) -> Result<(), String> {
    // 1. Add tool result messages to in-memory cache
    {
        let sessions = self.active_sessions.read().await;
        let session = sessions
            .get(&session_id)
            .ok_or_else(|| format!("Session not found: {}", session_id))?;

        let mut messages = session.messages.write().await;
        messages.extend(accumulated_messages.iter().cloned());
    }

    // 2. Emit UI update events for each tool result message
    for msg in &accumulated_messages {
        self.emit_event(AgentEvent::MessageAdded {
            session_id: session_id.clone(),
            message_id: msg.id.clone(),
        })
        .await?;
    }

    // 3. Persist to DB asynchronously
    let messages_for_db = accumulated_messages.clone();
    let session_id_clone = session_id.clone();
    tokio::spawn(async move {
        let message_repo = crate::state::get_message_repository();
        for msg in messages_for_db {
            if let Err(e) = message_repo.insert(&msg).await {
                log::error!(
                    "Failed to save tool result to DB: session={}, msg_id={}, error={}",
                    session_id_clone,
                    msg.id,
                    e
                );
            }
        }
    });

    // 4. Request next LLM completion with updated in-memory messages
    self.request_llm_completion(session_id).await?;
    Ok(())
}
```

### 2. 메모리 사용량 프로파일링

**목적**: In-memory cache로 인한 메모리 증가량 측정

**조사 방법**:

- Session당 평균 메시지 수 분석 (DB 쿼리)
- Message 구조체 크기 계산 (sizeof + dynamic fields)
- 동시 활성 세션 수 추정

**예상 계산**:

```
Message 크기: ~2KB (content, tool_calls 포함)
Session당 메시지: 100개 평균
→ 200KB per session

활성 세션 10개 가정:
→ 2MB 메모리 사용

최대 1000개 메시지/세션:
→ 20MB per session (worst case)
```

### 3. DB 동기화 실패 처리 전략

**목적**: 비동기 DB 저장 실패 시 대응 방안 결정

**옵션**:

1. **로그만 남기고 무시** (현재 제안)
   - 장점: 성능 영향 없음
   - 단점: 재시작 시 메시지 손실 가능

2. **재시도 큐 구현**
   - 장점: 데이터 일관성 보장
   - 단점: 복잡도 증가

3. **동기화 실패 시 사용자에게 알림**
   - 장점: 투명성
   - 단점: UX 방해 가능

**결정 필요**: 사용자 의사결정 필요

### 4. MessageAdded 페이로드 구조 결정

**Option A**: 전체 `message: Message` 포함

```rust
MessageAdded {
    session_id: String,
    message: Message,  // Full object
}
```

- 장점: Frontend에서 추가 DB 쿼리 불필요
- 단점: Event payload 크기 증가 (~2KB)

**Option B**: `message_id`만 전송, Frontend에서 조회

```rust
    session_id: String,
```

- 장점: Event payload 최소화
- 단점: Frontend에서 DB 쿼리 필요, 지연 발생

**결정 필요**: 성능 vs. 일관성 trade-off

### ✅ Q3: 대용량 세션 메시지 관리

**결정**: **Option C - Sliding Window (최근 1000개만 캐시)**

**근거**:

- Option A는 무제한 메모리 증가 (2000개 세션 시 2000개 전부 메모리에 유지)
- Option C는 메모리 footprint 고정 (~2MB per session)
- LLM context window와도 일치 (대부분 모델이 최근 히스토리만 필요)

**구현 방침**:

```rust
const MAX_CACHED_MESSAGES: usize = 1000;

impl AgentSessionManager {
    async fn add_message_to_cache(
        &self,
        session_id: &str,
        message: Message
    ) -> Result<(), String> {
        let sessions = self.active_sessions.read().await;
        let session = sessions.get(session_id)
            .ok_or_else(|| format!("Session not found: {}", session_id))?;

        let mut messages = session.messages.write().await;
        messages.push(message);

        // Apply sliding window policy
        if messages.len() > MAX_CACHED_MESSAGES {
            let removed = messages.remove(0);
            log::debug!(
                "Sliding window: removed oldest message {} from cache",
                removed.id
            );
        }

        Ok(())
    }
}
```

**장점**:

- 메모리 사용량 예측 가능 (1000 × 2KB = 2MB 고정)
- 긴 세션에서도 성능 안정적
- 오래된 메시지는 DB에 유지되어 필요 시 조회 가능

---

### ✅ Q4: Session 종료 시 메모리 해제

**결정**: **Option A - active_sessions에서 제거 시 자동 해제**

**근거**:

- Rust의 RAII (Resource Acquisition Is Initialization)로 자동 관리
- `Arc<RwLock<Vec<Message>>>` 참조가 모두 drop되면 자동 해제
- 명시적 clear() 불필요

**구현 방침**:

```rust
// active_sessions에서 제거만으로 충분
let mut sessions = self.active_sessions.write().await;
sessions.remove(&session_id);
// Arc refcount가 0이 되면 자동으로 메모리 해제
```

- 기존 사용자도 자연스럽게 새 아키텍처 사용

## 예상 리스크 및 대응 방안

### 리스크 1: 동시성 이슈 (Race Condition)

**시나리오**: 여러 tool 결과가 동시에 처리될 때 message cache 충돌

**시나리오**: Session이 종료되지 않고 계속 유지되면 메모리 증가
**대응**: Session timeout 메커니즘 구현 (기존에 있는지 확인 필요)

### 리스크 3: DB-Memory 불일치

**시나리오**: 비동기 저장 실패 후 재시작 시 메시지 손실
**대응**: 중요도 낮음으로 판단, 로그로 추적 가능하도록 설정
