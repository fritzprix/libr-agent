# Refactoring Plan: Complete Session Isolation & Global Manager Removal

## 1. 작업 목적 (Purpose)

- **완전한 세션 격리 구현**: 모든 MCP 연결(HTTP + Stdio)을 세션별로 독립 관리하여 진정한 Multi-Session 지원
- **Global Manager 제거**: 상태 확인 기능 및 Global connections 제거로 아키텍처 단순화
- **HTTP 세션 ID 관리 정상화**: 각 세션마다 올바른 `Mcp-Session-Id` 헤더를 사용하도록 수정

## 2. 현재 상태 / 문제점 (Current Status / Problems)

### 2.1 HTTP 연결의 치명적 결함

**Global Manager의 HTTP 연결 생성 (src-tauri/src/mcp/server/lifecycle.rs):**

```rust
// Line 118-121: reqwest client 생성 시 default_headers 설정
if let Some(sid) = session_id {
    header_map.insert("Mcp-Session-Id", sid);
}
let client = reqwest::Client::builder()
    .default_headers(header_map)  // ⚠️ 생성 시점에 고정됨
    .build()?;
```

**문제:**

- reqwest client의 `default_headers`는 생성 시점에 고정되어 **변경 불가능**
- 첫 세션의 session_id가 헤더에 박히면 다른 세션들도 **동일한 ID로 요청**
- 결과: 다중 세션에서 HTTP MCP 서버 사용 시 **다른 세션의 컨텍스트로 실행됨**

### 2.2 HttpSessionManager의 미구현 상태

**설계 의도:**

```rust
/// Unlike stdio servers which need isolated processes, HTTP servers are shared
/// across sessions but inject the session ID via the Mcp-Session-Id header.
```

**실제 상황:**

- `HttpSessionManager` 코드는 존재하지만 **전혀 사용되지 않음**
- `create_proxy` 호출 시 HTTP 서버 연결을 세션별로 생성하는 로직 **없음**
- Global Manager의 HTTP 연결을 그대로 공유하는 구조

### 2.3 상태 확인 기능의 부작용

**Frontend의 connectServers (MCPServerContext.tsx):**

```typescript
const rawToolsByServer = await listToolsFromConfig(mcpConfig);
```

**문제 발생 경로:**

1. UI에서 "상태 확인" 버튼 클릭
2. `list_tools_from_config` → 모든 서버(HTTP + Stdio)를 Global Manager에 연결
3. 첫 세션(또는 임의 세션)의 session_id가 HTTP 헤더에 고정
4. 이후 모든 세션이 **잘못된 session_id로 HTTP 서버와 통신**

## 3. 변경 이후의 상태 (Target State)

### 3.1 완전한 세션 격리

**모든 MCP 연결은 `MCPServiceProxy` 생성 시 세션별로 독립 생성:**

- **Stdio 서버**: `SessionMCPManager` (이미 구현됨)
- **HTTP 서버**: `HttpSessionManager` 활성화 (새로운 reqwest client 생성)
- **Builtin 서버**: `MCPServiceProxy` 내부 (이미 격리됨)

### 3.2 Global Manager 제거

**제거 대상:**

1. `MCPServerManager.connections` (HTTP/Stdio 통합 관리)
2. `list_tools_from_config` Tauri 명령어
3. `MCPServiceProxyManager.list_all_external_tools()` 함수
4. Frontend의 `connectServers` / `listToolsFromConfig` 로직

**대체 방안:**

- 세션 생성 시 Eager Tool Discovery로 도구 자동 수집 (Stdio는 이미 구현, HTTP 추가 필요)
- Agent 시작 전 도구 목록을 UI에 표시하려면 임시 세션을 생성하여 조회 후 삭제

### 4.2 Eager Tool Discovery - HTTP 서버 추가

**파일:** `src-tauri/src/mcp/service_proxy_manager.rs`

**수정 위치:** `create_proxy` 함수의 Eager Tool Discovery 섹션

```rust
// 현재: Stdio 서버만 처리 (Line 245-280)
for server_name in stdio_configs.keys() {
    // ... stdio tool discovery
}

// ✅ 추가: HTTP 서버도 처리
for server_name in http_configs.keys() {
    log::debug!(
        "Fetching tools from session HTTP server '{}' for session '{}'",
        server_name,
        session_id
    );

    if let Some(manager) = http_managers.get(&session_id) {
        match manager.list_tools(server_name).await {
            Ok(tools) => {
                let prefixed_tools: Vec<_> = tools
                    .into_iter()
                    .map(|mut tool| {
                        tool.name = format!("{}__{}", server_name, tool.name);
                        tool
                    })
                    .collect();

                proxy_arc
                    .set_session_http_tools(server_name.clone(), prefixed_tools)
                    .await;
            }
            Err(e) => {
                log::error!("Failed to fetch HTTP tools: {:?}", e);
            }
        }
    }
}
```

### 4.3 MCPServiceProxy 확장

**파일:** `src-tauri/src/mcp/service_proxy.rs`

**추가 필드:**

```rust
pub struct MCPServiceProxy {
    // ... 기존 필드

    /// Cached tools from session-isolated HTTP servers
    session_http_tool_cache: Arc<RwLock<HashMap<String, Vec<MCPTool>>>>,

    /// Session-specific HTTP manager
    http_manager: Arc<HttpSessionManager>,
}
```

**추가 메서드:**

```rust
impl MCPServiceProxy {
    pub async fn get_session_http_tools(&self) -> Vec<MCPTool> {
        let cache = self.session_http_tool_cache.read().await;
        cache.values().flatten().cloned().collect()
    }

    pub async fn set_session_http_tools(&self, server_name: String, tools: Vec<MCPTool>) {
        let mut cache = self.session_http_tool_cache.write().await;
        cache.insert(server_name, tools);
    }
}
```

## 5. 해결 판정 기준 (Acceptance Criteria)

1. **다중 세션 HTTP 지원**: 여러 Agent 세션이 동시에 실행될 때, 각 세션이 **자신의 session_id로** HTTP MCP 서버와 통신
2. **Global Manager 의존성 제거**: `collect_available_tools`가 Global Manager의 `list_all_tools`를 호출하지 않음
3. **상태 확인 기능 제거**: Frontend에서 `listToolsFromConfig`를 호출하지 않음
4. **세션 생성 시 자동 도구 수집**: HTTP와 Stdio 도구가 모두 Eager Tool Discovery로 수집됨
5. **빌드 성공**: Rust 컴파일 및 Frontend 빌드 에러 없음

### Q1: Frontend 상태 확인 기능 대체 방안

**현재 동작:**

- 사용자가 Assistant 편집 시 "상태 확인" 버튼으로 MCP 서버 도구 목록 미리 확인

**Option 1 (권장):**

- 세션 시작 후 도구 목록 자동 표시
- 장점: 아키텍처 단순화, 다중 세션 지원
- 단점: 사용자가 세션 시작 전 도구를 볼 수 없음

**Option 2 (호환성 유지):**

- 임시 세션 생성 → 도구 조회 → 세션 삭제
- 장점: 기존 UX 유지
- 단점: 추가 구현 비용, 서버 부하

**결정 필요:**

- UI/UX 변경 허용 여부
- 기존 사용자 워크플로우 영향도

### Q2: HTTP 연결 관리 방식

**Option 1: 세션마다 독립 reqwest client**

- 각 세션이 자신의 client 보유
- 장점: 완전한 격리, session_id 관리 명확
- 단점: 연결 풀 중복, 메모리 사용 증가

**Option 2: 공유 client + 요청 시 헤더 주입**

- Global client 사용, 요청마다 session_id 헤더 주입
- 장점: 리소스 효율적
- 단점: reqwest API로는 불가능 (default_headers 고정)

**권장:**

- Option 1 선택 (현재 rmcp 라이브러리 구조상 유일한 방법)
