## 작업의 목적 (Purpose)

Agent의 Content Store 도구 사용 시 발생하는 **무한 읽기 루프**와 **잘못된 범위 추정** 문제를 해결하여 AI Agent의 효율성을 개선하고 불필요한 API 호출 비용을 절감합니다.

**핵심 목표:**

1. Truncation 플래그의 오해를 방지하여 Agent가 파일 끝을 정확히 인식하도록 개선
2. Line count 정보를 가시화하여 Agent가 유효한 범위를 추정할 수 있도록 지원
3. 에러 메시지를 구체화하여 범위 초과 오류 시 즉시 복구 가능하도록 개선

---

## 현재의 상태 / 문제점 (Current State & Problems)

### Problem 1: 잘못된 Truncation 플래그 (Critical)

**현상:**

- Agent가 `readContent(fromLine=1, toLine=100)`을 호출하여 전체 내용(86줄)을 받았음에도 `... (truncated, 4438 bytes total)` 메시지를 받음
- Agent가 이를 "중요한 데이터가 남아있음"으로 해석
- `fromLine=1001`, `fromLine=5000` 등 무효한 범위로 5회 이상 재시도
- 결과: 불필요한 API 호출, 시간 낭비, 비용 증가

**근본 원인:**

```rust
// src-tauri/src/mcp/builtin/content_store/handlers.rs:450-456
let content_preview = if content.len() > 2000 {
    format!(
        "{}\n... (truncated, {} bytes total)",
        content.chars().take(2000).collect::<String>(),
        content.len()
    )
} else {
    content.clone()
};
```

- **단순 바이트 길이**만으로 truncation 판정 (`> 2000 bytes`)
- 요청한 라인 범위가 완전히 반환되었는지 확인하지 않음
- 남은 컨텐츠의 의미를 평가하지 않음 (공백, 줄바꿈만 남은 경우 등)

### Problem 2: Line Count 정보 부재 (Medium-High)

**현상:**

- Agent는 파일 크기만 알 수 있음: `Size: 4441 bytes`
- Line count는 JSON에만 존재하고 텍스트 출력에 없음
- Agent가 바이트 수로 라인 수를 추측하다 실패 (5000줄 요청 → 실제 86줄)

**근본 원인:**

```rust
// src-tauri/src/mcp/builtin/content_store/handlers.rs:307
format!(
    "[{}] ID: {}\n    Title: {}\n    Size: {} bytes\n    Preview: {}\n    Created: {}",
    idx + 1, item.id, item.filename, item.size, preview_text, item.uploaded_at
)
```

- Human-readable 출력에 `line_count` 미포함
- JSON `response.data.lineCount`에는 존재하지만 Agent가 텍스트 요약에 의존

### Problem 3: 모호한 에러 메시지 (Medium)

**현상:**

- `readContent(fromLine=5000, toLine=5300)` 호출 시 (실제 파일: 86줄)
- 에러: `"No content found in specified line range"`
- Agent가 이를 "검색 실패"로 해석하여 범위를 더 넓게 재시도

**근본 원인:**

```rust
// src-tauri/src/mcp/builtin/content_store/storage.rs:485-487
if result.is_empty() {
    return Err("No content found in specified line range".to_string());
}
```

- 단일 에러 메시지로 여러 실패 케이스 처리
- 실제 파일 크기 정보 미제공
- "범위 초과" vs "빈 결과" 구분 불가

## 관련 코드의 구조 및 동작 방식 Summary (Architecture Overview)

### Content Store 읽기 플로우

```
Agent Request
    ↓
Frontend: useUnifiedMCP.executeTool("readContent", params)
    ↓
Tauri IPC: invoke("builtin_mcp_call_tool")
    ↓
Backend: ContentStoreServer.handle_read_content(params)
    ↓
Storage: ContentStoreStorage.read_content(content_id, from_line, to_line)
    ↓
Chunk Processing: Filter & extract lines from chunks
    ↓
Handlers: Format response with SuccessHint
    ↓
Return: { text: "...", data: { content, lineRange } }
```

### 핵심 컴포넌트

1. **Storage Layer** (`storage.rs`)
   - 실제 청크에서 라인 추출
   - 에러 메시지 생성
   - Line range validation (현재 미흡)

2. **Handlers Layer** (`handlers.rs`)
   - Request validation
   - Truncation logic 적용
   - Human-readable output 생성
   - SuccessHint 구성

3. **Data Model** (`storage.rs:17-32`)
   - `ContentItem` 구조체에 `line_count` 필드 존재
   - `listContent` 응답에서 JSON으로 전달
   - Human-readable 출력에서 누락

### Change 3: Enhance Error Messages (P1)

**File:** `src-tauri/src/mcp/builtin/content_store/storage.rs`  
**Location:** Lines 455-490  
**Function:** `read_content()`

#### Before:

```rust
pub async fn read_content(
    &self,
    content_id: &str,
    from_line: usize,
    to_line: Option<usize>,
) -> Result<String, String> {
    let chunks = self
        .chunks
        .get(content_id)
        .ok_or_else(|| format!("Content '{content_id}' not found"))?;

    let mut result = String::new();
    let target_to_line = to_line.unwrap_or(usize::MAX);

    for chunk in chunks {
        if chunk.line_range.1 >= from_line && chunk.line_range.0 <= target_to_line {
            // Chunk overlaps with requested range
            let lines: Vec<&str> = chunk.text.lines().collect();
            let start_idx = from_line.saturating_sub(chunk.line_range.0);

            let end_idx = if chunk.line_range.1 > target_to_line {
                target_to_line - chunk.line_range.0 + 1
            } else {
                lines.len()
            };

            for line in lines.iter().take(end_idx.min(lines.len())).skip(start_idx) {
                result.push_str(line);
                result.push('\n');
            }
        }
    }

    if result.is_empty() {
        return Err("No content found in specified line range".to_string());
    }

    Ok(result.trim().to_string())
}
```

#### After:

```rust
pub async fn read_content(
    &self,
    content_id: &str,
    from_line: usize,
    to_line: Option<usize>,
) -> Result<String, String> {
    let chunks = self
        .chunks
        .get(content_id)
        .ok_or_else(|| format!("Content '{content_id}' not found"))?;

    // Calculate file boundaries
    let max_line = chunks.iter().map(|c| c.line_range.1).max().unwrap_or(0);
    let target_to_line = to_line.unwrap_or(max_line).min(max_line);

    // Validate range BEFORE processing
    if from_line < 1 {
        return Err(format!(
            "Error: Line numbers must start from 1 (requested: {}).",
            from_line
        ));
    }

    if from_line > max_line {
        return Err(format!(
            "Error: Requested range [{}-{}] exceeds file length.\n\
             File has {} lines. Valid range: [1-{}].\n\
             Use listContent to verify file size before reading.",
            from_line, target_to_line, max_line, max_line
        ));
    }

    let mut result = String::new();

    for chunk in chunks {
        if chunk.line_range.1 >= from_line && chunk.line_range.0 <= target_to_line {
            // Chunk overlaps with requested range
            let lines: Vec<&str> = chunk.text.lines().collect();
            let start_idx = from_line.saturating_sub(chunk.line_range.0);

            let end_idx = if chunk.line_range.1 > target_to_line {
                target_to_line - chunk.line_range.0 + 1
            } else {
                lines.len()
            };

            for line in lines.iter().take(end_idx.min(lines.len())).skip(start_idx) {
                result.push_str(line);
                result.push('\n');
            }
        }
    }

    if result.is_empty() {
        // This should rarely happen now due to pre-validation
        return Err(format!(
            "No content found in line range [{}-{}]. File has {} lines.",
            from_line, target_to_line, max_line
        ));
    }

    Ok(result.trim().to_string())
}
```

## Clarification Q-list (검토 필요 사항)

### Q1: Truncation Threshold ✅ **ANSWERED**

**질문:** 현재 2000 바이트 기준으로 preview를 자르고 있습니다. 이 값을 유지할지, 조정할지 결정이 필요합니다.

**옵션:**

- A) 2000 bytes 유지 (현재 값) ✅ **SELECTED**
- B) 5000 bytes로 증가 (더 많은 컨텍스트 제공)
- C) 동적 조정 (파일 크기 기반)

**답변:** **Option A - 2000 bytes 유지**

**근거:**

- Byte truncation은 **데이터 제한이 아닌 display 최적화** 목적 ([분석 문서](../analysis/byte_truncation_analysis_20260110.md) 참조)
- Full data는 `structured_content.content`에 항상 완전하게 존재
- `content[0].text`는 LLM이 읽는 preview (context window 절약용)
- 2000 bytes는 약 30-40줄 코드로 충분한 context 제공
- 문제는 threshold가 아니라 **메시지 표현** (preview truncation vs file truncation 구분 필요)

---

### Q2: Line Count Calculation Method ✅ **ANSWERED**

**질문:** Line count는 현재 `content.lines().count()`로 계산됩니다. 다른 정의가 필요한지 확인 필요합니다.

**옵션:**

- A) `\n` 기준 (current) ✅ **SELECTED**
- B) `\r\n` 포함 처리
- C) Empty lines 제외 (실제 코드 라인만)

**답변:** **Option A - `\n` 기준 유지 (current)**

**근거:**

- Rust의 `.lines()` iterator는 `\n`, `\r\n`, `\r` 모두 자동 처리 (cross-platform)
- Empty lines 포함이 표준 (VS Code, GitHub, 모든 에디터와 일치)
- "Line 50" 요청 시 에디터의 Line 50과 정확히 대응되어야 함
- Empty lines 제외하면 agent와 editor 간 line number 불일치 발생
- User suggestion (Option C)는 rejected: Line count는 물리적 줄 수여야 하며, 코드 줄만 세는 것은 별도 metric (SLOC)

---

### Q3: Error Recovery Strategy ✅ **ANSWERED**

**질문:** Out of bounds 에러 발생 시 자동 조정 로직을 추가할지 결정 필요합니다.

**옵션:**

- A) 에러만 반환 (Agent가 판단) ✅ **SELECTED**
- B) 자동으로 valid range로 조정하여 읽기
- C) 경고와 함께 조정된 결과 반환

**답변:** **Option A - 에러만 반환 (Agent가 판단)**

**근거:**

- User suggestion (Option B) rejected - 자동 조정은 silent failure를 만듦
- Explicit error가 agent에게 더 나은 학습 기회 제공
- Enhanced error message에 valid range 포함으로 충분:
  ```
  Error: Range [5000-5300] exceeds file length.
  File has 86 lines. Valid range: [1-86]
  ```
- Agent가 정확한 bounds를 알고 재시도하는 것이 robust
- 자동 조정 시 agent는 왜 다른 데이터를 받았는지 모름
- Principle: "Errors should be loud, not silent"

---

### Q4: Structured Data Enhancement

**질문:** JSON `response.data`에 추가 메타 ✅ **ANSWERED**
**질문:** JSON `response.data`에 추가 메타데이터를 포함할지 결정 필요합니다.

**현재:**

```json
{
  "content": "...",
  "lineRange": [1, 100]
}
```

**제안:**

```json
{
  "content": "...",
  "lineRange": [1, 100],
  "totalLines": 86,
  "isComplete": true,
  "remainingLines": 0,
  "suggestedNextRange": null
}
```

**답변:** **YES - Add enhanced metadata**

**근거:**

- User comment "structured data is for UI" is **partially correct** but incomplete
- While UI can use it, **agents CAN also parse structured_content** if they're sophisticated
- Adding metadata has **zero cost** (already computed) and **high benefit**:
  - `totalLines`: Agent can calculate valid ranges
  - `isComplete`: Agent knows if more data exists
  - `remainingLines`: Quick check for continuation need
  - `suggestedNextRange`: Helpful hint for next read
- Follows principle: **"Make the right thing easy"**
- No breaking change (existing fields preserved)
- Future-proof for smarter agents that do parse JSON
