# Agent V2 Production UI/UX Implementation Plan

**Date**: 2024-12-30 15:00  
**Status**: Planning Phase  
**Target**: Replace prototype AgentChatView with production-ready compound component architecture

---

## 1. 작업의 목적 (Work Purpose)

**Primary Goal**: Implement fully functional production UI/UX for Agent V2 while maintaining 100% backward compatibility with legacy Chat (V1) system.

**Specific Objectives**:

1. Create production-ready `AgentChatStartView` with two-column layout (assistant selection + session history)
2. Refactor `AgentChatView` to compound component pattern matching `Chat.tsx` architecture
3. Ensure complete isolation between V1 (`ChatContext`) and V2 (`AgentChatContext`) systems
4. Provide consistent UX across both chat systems while leveraging Agent V2's backend orchestration

- `src/features/agent/AgentChatView.tsx` - Simple prototype with inline UI

## 3. 관련 코드의 구조 및 동작 방식 Summary (Bird's Eye View)

### Architecture Comparison

**V1 Chat System (Legacy)**:

```
User Input
  ↓
ChatContext (Frontend Orchestration)
  ↓
useAIService (Direct LLM calls)
  ↓
Tool Execution (Frontend loop)
  ↓
IndexedDB Storage
```

**V2 Agent System (New)**:

```
User Input
  ↓
AgentChatContext (UI State Manager)
  ↓
Tauri IPC → AgentSessionManager (Rust)
  ↓
Event-Driven Orchestration:
  - llm:completion-request → LLMServiceContext
  - tool:execute-request → MCPServiceProxy (Rust)
  - agent:event → UI Updates
  ↓
SQLite Storage (Source of Truth)
```

### Component Interaction Flow

```
App.tsx
  ├─ ChatProvider (V1)           ← Keep as-is
  │    └─ Chat.tsx
  │         ├─ Chat.Header
  │         ├─ Chat.Messages
  │         └─ Chat.Input
  │
  └─ AgentSessionProvider (V2)   ← New system
       └─ AgentChatProvider (V2)
            └─ AgentChatView.tsx (NEW)
                 ├─ AgentChatView.Header (NEW)
                 ├─ AgentChatView.StatusBar (NEW)
                 ├─ AgentChatView.Messages (NEW)
                 ├─ AgentChatView.Input (NEW)
                 └─ AgentChatView.Bottom (NEW)
```

### Key Context Dependencies

```typescript
// V1 System (Legacy - DO NOT TOUCH)
ChatContext → useAIService → IndexedDB
SessionContext → IndexedDB

// V2 System (New Implementation)
AgentSessionContext → Rust AgentSessionManager → SQLite
AgentChatContext → Listens to agent:event
LLMServiceContext → Executes llm:completion-request
```

## 6. Panel State Management Pattern Analysis

Based on V1 implementation analysis (see `docs/analysis/v1-panel-state-management-patterns.md`), two distinct patterns exist:

### Pattern 1: Service Context Pattern (Recommended)

**Used By**: `ChatPlanningPanel`

**Architecture**:

```
Web MCP Server → getServiceContext() → BuiltInToolProvider
  → serviceContexts[serviceId] → useServiceContext<T>()
  → UI Component (Automatic Updates)
```

**Characteristics**:

- ✅ Declarative state subscription
- ✅ Automatic updates via `buildToolPrompt()` calls
- ✅ Session/thread isolation built-in
- ✅ TypeScript-typed structured state
- ✅ Integrated with LLM context (system prompt)
- ✅ Reusable across components

**Update Timing**:

- Before each LLM request (via `llm:completion-request` in Agent V2)
- On session context switch
- Via `useMessageTrigger` (manual)

### Pattern 2: Direct Backend Pattern

**Used By**: `WorkspaceFilesPanel`

**Architecture**:

```
UI Action → Direct Rust Command (Tauri IPC)
  → Manual State Update → UI Re-render
```

**Characteristics**:

- ✅ Performance-optimized (on-demand)
- ✅ Fine-grained control
- ✅ Dynamic state (file system)
- ❌ More boilerplate
- ❌ No automatic LLM integration

### Agent V2 Pattern Selection

**Planning Panel** → **Service Context Pattern** ✅

- Structured state (goals, todos, scratchpad)
- Needs LLM integration for context
- Multiple components may need same state
- Session isolation critical

**Workspace Panel** → **Service Context Pattern** ✅

- Consistency with planning panel
- Easier maintenance
- Built-in session isolation
- Future optimization possible if needed

**Critical Note**: Service Context updates are NOT real-time. They occur:

1. Before each LLM request (`buildToolPrompt()` call)
2. For Agent V2: This is PERFECT timing (Rust orchestrator triggers `llm:completion-request`)
3. State will be fresh for every agent workflow cycle

```typescript
// Separate from V1 ChatPlanningContext (different session system)
// Manages planning panel state for Agent V2

import { createContext, useContext, useState } from 'react';
import { useAgentSessionState } from './AgentSessionContext';

interface AgentPlanningContextValue {
  showPlanningPanel: boolean;
  togglePlanningPanel: () => void;
}

const AgentPlanningContext = createContext<AgentPlanningContextValue | null>(null);

export function AgentPlanningProvider({ children }: { children: React.ReactNode }) {
  const [showPlanningPanel, setShowPlanningPanel] = useState(false);

  const togglePlanningPanel = () => {
    setShowPlanningPanel((prev) => !prev);
  };

  return (
    <AgentPlanningContext.Provider value={{ showPlanningPanel, togglePlanningPanel }}>
      {children}
    </AgentPlanningContext.Provider>
  );
}

export function useAgentPlanning() {
  const context = useContext(AgentPlanningContext);
  if (!context) throw new Error('useAgentPlanning must be used within AgentPlanningProvider');
  return context;
}
```

## 12. Risk Mitigation

### Potential Issues

1. **State Synchronization Complexity**
   - Risk: React state vs SQLite state mismatch
   - Mitigation: Follow idea.md architecture (React owns UI state, no DB reload during workflow)

2. **Performance with Many Sessions**
   - Risk: Session list load time
   - Mitigation: Pagination, lazy loading, virtual scrolling

3. **Session Isolation**
   - Risk: Cross-session state leakage
   - Mitigation: Strict sessionId checks, per-session MCP proxies

4. **Backward Compatibility Breaking**
   - Risk: Accidentally modifying V1 code
   - Mitigation: Clear file structure, code review checklist

### Rollback Plan

If critical issues arise:

1. Feature flag: Toggle between V1 and V2 in settings
2. Route redirect: /agent → /chat fallback
3. Independent deployment: V2 can be disabled without affecting V1

## 13. Clarification Q-List (질문 목록)

### Design Questions

**Q1**: Should AgentChatStartView support multi-agent selection for collaborative sessions?

- **Context**: Current plan is single assistant per session
- **Options**:
  - A) Single assistant only (simpler, Phase 1)
  - B) Multi-select assistants (complex, Phase 2+)
- **Impact**: UI design (checkboxes vs radio), session creation logic
  > Answer is 'A', the Agent will create new agent session if they needs

**Q2**: Session delete confirmation - Modal or inline confirm?

- **Context**: Deleting session is destructive
- **Options**:
  - A) Modal dialog (more explicit)
  - B) Inline confirmation (faster)
  - C) Undo toast after delete (modern pattern)
- **Impact**: UX flow, implementation complexity

> Answer is 'B' inline confirm

**Q3**: Should completed/error sessions be auto-archived after X days?

- **Context**: Session list could grow large
- **Options**:
  - A) No auto-archive (manual cleanup)
  - B) Auto-archive with user setting
  - C) Archive view (separate tab)
- **Impact**: Database design, UI complexity

> Answer is 'A' no auto-archive

### Technical Questions

**Q4**: AgentChatAttachedFiles - Implement in Phase 1 or defer?

- **Context**: File attachments not in V2 backend yet
- **Options**:
  - A) Placeholder component (Phase 1)
  - B) Full implementation (requires backend work)
  - C) Omit entirely until backend ready
- **Impact**: Feature completeness, timeline

> Answer is 'B' and you can refer the legacy code, fyi, the attached file is parsed and added to content-store that support keyword similarity search

**Pattern Decision**: Use Service Context Pattern for consistency. The content-store server should implement `getServiceContext()` to expose attached files state.

**Q5**: Message virtualization - When to implement?

- **Context**: Long conversations may have 1000+ messages
- **Options**:
  - A) Start with simple scroll (Phase 1)
  - B) Implement virtualization from start (complex)
  - C) Add when performance issues arise (Phase 3+)
- **Impact**: Performance, complexity

> Answer is 'A', but 1000 messages are hard limit of how many messages are loaded, we can support window sliding by 10 over 1000 messages by infinite scrolling

**Q6**: Session resume - Load all messages or paginate?

- **Context**: SQLite can have large message history
- **Options**:
  - A) Load all (simple, may be slow)
  - B) Load last N messages (faster, need pagination UI)
  - C) Lazy load on scroll (complex, best UX)
- **Impact**: Initial load time, implementation complexity

> Answer is `C`

### Scope Questions

**Q7**: Should we implement session search/filter in Phase 1?

- **Context**: User might have many sessions
- **Options**:
  - A) Just sort by status (Phase 1)
  - B) Add search input (Phase 2)
  - C) Advanced filters (Phase 3+)
- **Impact**: Feature scope, timeline

> Answer is A and B

**Q8**: Export/Import session configuration - Include in scope?

- **Context**: Users may want to share agent setups
- **Options**:
  - A) Not in initial scope
  - B) Export only (Phase 2)
  - C) Full import/export (Phase 3)
- **Impact**: Feature scope, data format design

> Answer is `A`

Note: We have workspacepanel and planningpanel in Chat.tsx and AgentChatView also need same stuffs to show the status of both tools to users
