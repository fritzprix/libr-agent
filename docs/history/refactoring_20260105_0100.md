# Refactoring Plan: Phase 2 - Playbook Module Migration to SeaORM

## 1. 작업의 목적 (Purpose)

Playbook 모듈의 데이터베이스 상호작용을 raw SQLx 쿼리에서 **SeaORM**으로 마이그레이션하여 타입 안정성, 유지보수성, 스키마 관리 능력을 향상시킨다. 이는 Planning 모듈 마이그레이션(Phase 1) 이후의 연속 작업으로, 일관된 ORM 패턴을 프로젝트 전반에 적용하는 것을 목표로 한다.

## 2. 현재의 상태 / 문제점 (Current State / Problems)

### 2.1 Raw SQL 쿼리 의존성

- **`mod.rs`**: `init_tables()` 함수에서 `CREATE TABLE` 및 인덱스 생성을 위해 raw SQL 문자열 사용
- **`operations.rs`**: 9개 이상의 함수에서 `sqlx::query()` 직접 호출
  - `create_playbook`: INSERT 쿼리 (Line 76)
  - `list_playbooks`: 동적 SELECT 쿼리, 페이지네이션 포함 (Line 178-192)
  - `get_playbook`: SELECT by ID (Line 352)
  - `select_playbook`: SELECT for execution (Line 407)
  - `delete_playbook`: DELETE by ID (Line 499)
  - `update_playbook`: UPDATE all fields (Line 619)

### 2.2 JSON 직렬화 문제

- `workflow` 필드: `Vec<PlaybookStep>` → JSON 문자열로 수동 변환
- `success_criteria` 필드: `Option<SuccessCriteria>` → JSON 문자열로 수동 변환
- 에러 발생 시 런타임에 패닉 가능성 (`unwrap_or_default()` 사용)

### 2.3 수동 데이터 매핑

- **`types.rs`**: `Playbook::from_row()` 메서드로 `SqliteRow`에서 수동 역직렬화
  - JSON 필드 파싱 에러 시 기본값으로 대체 (`unwrap_or_default()`)
  - 타입 안정성 부족

### 2.4 동적 쿼리 빌딩 복잡성

- `list_playbooks`에서 페이지네이션에 따라 LIMIT/OFFSET 조건을 동적으로 생성
- 쿼리 문자열 조합으로 인한 가독성 저하

## 3. 관련 코드의 구조 및 동작 방식 Summary (Bird's-Eye View)

### 3.1 모듈 구조


### 3.2 데이터베이스 스키마

```sql
CREATE TABLE playbooks (
    id TEXT NOT NULL,
    session_id TEXT NOT NULL,
    goal TEXT NOT NULL,
    initial_command TEXT,
    workflow JSON NOT NULL,
    success_criteria JSON,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    PRIMARY KEY (id, session_id),
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
)
```

### 3.3 주요 동작 흐름

1. **생성**: `create_playbook` → JSON 직렬화 → INSERT → SELECT 재조회 → `from_row()` 역직렬화
2. **조회**: `list_playbooks` → 동적 쿼리 빌딩 → COUNT + SELECT → `from_row()` 변환 → 페이지네이션 메타데이터 생성
3. **업데이트**: `update_playbook` → 기존 데이터 SELECT → 필드 병합 → JSON 직렬화 → UPDATE
4. **삭제**: `delete_playbook` → DELETE → rows_affected 확인

## 4. 변경 이후의 상태 / 해결 판정 기준 (Future State / Success Criteria)

### 4.1 SeaORM Entity 정의

- `playbooks` 테이블을 SeaORM Entity로 정의
- JSON 필드는 `#[sea_orm(column_type = "Json")]` 속성 사용
- Composite Primary Key (`id`, `session_id`) 지원

### 4.2 타입 안전 쿼리

- 모든 CRUD 작업에서 `Entity::find()`, `ActiveModel::save()` 등 SeaORM API 사용
- `sqlx::query()` 제거

### 4.3 자동 JSON 처리

- `workflow` 및 `success_criteria` 필드는 SeaORM이 자동으로 직렬화/역직렬화

### 4.5 성능 기준

- 쿼리 성능이 기존 대비 10% 이내 유지
- JSON 직렬화 오버헤드 최소화

```rust
}

pub struct SuccessCriteria {
    pub description: String,
    #[serde(rename = "requiredArtifacts")]
    pub required_artifacts: Option<Vec<String>>,
}

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, Serialize, Deserialize)]
#[sea_orm(table_name = "playbooks")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub id: String,

    #[sea_orm(primary_key, auto_increment = false)]
    #[sea_orm(indexed)]
    pub session_id: String,

    pub goal: String,
    pub initial_command: Option<String>,

    #[sea_orm(column_type = "Json")]
    pub workflow: Json, // Will hold Vec<PlaybookStep>

    #[sea_orm(column_type = "Json")]
    pub success_criteria: Option<Json>, // Will hold Option<SuccessCriteria>

    pub created_at: i64,

    #[sea_orm(indexed)]
    pub updated_at: i64,
}

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}

impl ActiveModelBehavior for ActiveModel {}

// Helper methods for JSON field conversion
impl Model {
    pub fn workflow_typed(&self) -> Result<Vec<PlaybookStep>, serde_json::Error> {
        serde_json::from_value(self.workflow.clone())
    }

    pub fn success_criteria_typed(&self) -> Option<SuccessCriteria> {
        self.success_criteria
            .as_ref()
            .and_then(|v| serde_json::from_value(v.clone()).ok())
    }
}
```

### 8.1 Composite Primary Key 동작 검증

- **Issue**: SeaORM의 composite primary key가 SQLite에서 예상대로 작동하는지 확인 필요
- **Action**: 단위 테스트로 (id, session_id) 조합의 유일성 검증

### 8.2 JSON 필드 성능 분석

- **Issue**: 큰 `workflow` 배열(100+ 단계)의 직렬화/역직렬화 성능
- **Action**: 벤치마크 테스트로 측정, 필요시 최적화 전략 수립

### 8.3 동적 페이지네이션 최적화

- **Issue**: `limit=-1`일 때 모든 결과를 가져오는 패턴이 대량 데이터에서 성능 문제 가능
- **Action**: 최대 결과 수 제한 또는 스트리밍 방식 도입 검토

### 8.4 UI 렌더링 로직 분리

- **Issue**: `render_ui()` 함수가 `operations.rs`에 있어 관심사 분리 위반
- **Action**: UI 관련 로직을 별도 모듈로 분리 (예: `ui.rs`)
