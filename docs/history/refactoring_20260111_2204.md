# Refactoring Plan: Add Primary Isolated Shell Execution Tools

**Date**: 2026-01-11  
**Target Version**: 0.4.0  
**Priority**: High  
**Estimated Effort**: Medium (4-6 hours)

---

## 작업의 목적 (Purpose)

Add new primary shell execution tools (`runShell` for Unix, `runPowerShell` for Windows) to provide quick, isolated, synchronous command execution for the most common use case (90% of shell commands). This addresses the current design where agents must use the heavyweight persistent shell infrastructure even for simple one-off commands like `ls`, `cat`, or `grep`.

**Key Goals:**

1. Reduce overhead for simple shell commands
2. Provide clear tool selection guidance for agents
3. Maintain workspace root anchoring consistency
4. Preserve existing persistent shell functionality for advanced use cases

---

## 현재의 상태 / 문제점 (Current State / Problems)

### Current Tool Architecture

1. **`runInPersistentShell` (Unix) / `runInPersistentPowerShell` (Windows)**
   - Primary tool agents use for all shell commands
   - Creates persistent shell session with state preservation
   - Overhead: Shell process management, state tracking, fallback logic
   - Use case: Only needed for 10% of commands (cd chains, export vars, venv activation)

2. **`spawnProcess`**
   - Background execution for long-running tasks
   - Not suitable for quick synchronous commands
   - Use case: Builds, downloads, training models

### Problems

1. **Performance Overhead**: Simple commands like `ls -la` create unnecessary persistent shell sessions
2. **Agent Confusion**: No clear tool for "just run a quick command"
3. **Resource Usage**: Every agent session maintains persistent shell even if unused
4. **Complexity**: Fallback logic in persistent shell masks the simpler use case

### Code Architecture

**File Structure:**

- `src-tauri/src/mcp/builtin/workspace/mod.rs` - Tool routing
- `src-tauri/src/mcp/builtin/workspace/tools/code_tools.rs` - Tool definitions
- `src-tauri/src/mcp/builtin/workspace/code_execution/shell.rs` - Execution logic
- `src-tauri/src/session_isolation.rs` - Isolation infrastructure
- `src-tauri/src/session.rs` - Session management

**Execution Flow (Current):**

```
runInPersistentShell
  → execute_shell_persistent
    → shell_manager.execute (persistent shell)
      → (on error) fallback → execute_shell_with_isolation
```

**Key Finding**: `execute_shell_with_isolation` already exists and provides exactly the behavior needed for the new tools.

```rust
// Add after handle_execute_shell method (around line 600)

async fn handle_run_shell(
    &self,
    args: &HashMap<String, Value>,
    session_id: &str,
) -> Result<MCPResult, String> {
    // Extract command
    let command = args
        .get("command")
        .and_then(|v| v.as_str())
        .ok_or_else(|| {
            missing_param_error("command", "Shell command to execute", ToolGroup::Workspace)
                .to_json_string()
        })?;

    // Extract timeout (optional, default from config)
    let timeout = args
        .get("timeout")
        .and_then(|v| v.as_u64())
        .unwrap_or(crate::config::default_execution_timeout());

    // Execute with Medium isolation (always workspace root anchored)
    self.execute_shell_with_isolation(
        command,
        IsolationLevel::Medium,
        timeout,
        session_id,
    )
    .await
}
```

## Clarification Q-List

### Q1: Tool Naming Convention

**Question**: Should we use `runShell` or `executeShell` for the new primary tool?

**Options**:

- A) `runShell` / `runPowerShell` (shorter, matches "run" pattern)
- B) `executeShell` / `executePowerShell` (more explicit, matches existing naming)

**Recommendation**: Option A (`runShell`) - Shorter, aligns with "spawnProcess" pattern, and creates clear distinction from "runInPersistentShell"

### Q2: Should Persistent Shell Tools Show Usage Warnings?

**Question**: Should persistent shell tools return warnings when used for simple commands that don't need state?

**Options**:

- A) Yes - Add usage hints in output when command doesn't use persistence features
- B) No - Let agents learn through documentation only
- C) Service context guidance only

**Recommendation**: Option C - Service context already guides agents; adding warnings to output may confuse or annoy users

### Q3: Default Timeout Value

**Question**: Should new isolated tools use the same default timeout as persistent shell?

**Current**: 30 seconds default for all shell tools

**Options**:

- A) Keep same (30 seconds)
- B) Lower for isolated tools (15 seconds) since they're for quick commands
- C) Make timeout required parameter (no default)

**Recommendation**: Option A - Keep consistency, agents can adjust if needed

### Q4: Error Output Format

**Question**: How should stderr be handled for isolated shell execution?

**Current Behavior**:

- Persistent shell includes stderr in error guidance
- Isolated execution (in fallback) shows stderr in structured_content only

**Options**:

- A) Always include stderr in text output (agents can see it)
- B) Only include stderr in structured_content (UI only)
- C) Include stderr in text only when exit_code != 0

**Recommendation**: Option C - Include stderr in text output for non-zero exit codes, following MCP Tool Response Design principles

### Q5: Service Context Update Timing

**Question**: When should we update service context to recommend new tools?

**Options**:

- A) Immediately with tool launch
- B) After testing period with feature flag
- C) Gradual rollout based on agent performance

**Recommendation**: Option A - Service context is guidance only, doesn't break existing functionality
