# Built-in Tool MCPResult Architecture Refactoring

## 작업의 목적

Built-in Web MCP Tool 서버들이 불필요하게 JSON-RPC 2.0 전송 계층(`MCPResponse`)을 생성하는 문제를 해결한다. Built-in Tool은 브라우저 내부에서 동작하므로 순수한 Tool 실행 결과(`MCPResult`)만 반환하고, 전송 계층 래핑은 Worker에서 일괄 처리하도록 아키텍처를 개선한다.

### 배경

- Built-in Tool과 External MCP Server의 아키텍처 차이를 명확히 구분
- Built-in Tool: 브라우저 내부 실행 → 전송 계층 불필요
- External MCP: stdio 통신 → JSON-RPC 2.0 필수
- 현재는 두 경우 모두 `MCPResponse` 생성으로 인한 중복 코드 및 복잡도 증가
- 이전 refactoring_20251116_2044.md에서 Message-MCP 통합 시 근본 문제 발견

### 핵심 문제

**불필요한 전송 계층 래핑:**

```typescript
// 현재: Built-in Tool이 직접 MCPResponse 생성 (불필요!)
async callTool(name: string, args: unknown): Promise<MCPResponse<unknown>> {
  return createMCPTextResponse('Success');
  // → { jsonrpc: '2.0', id: 'xxx', result: { content: [...] } }
}
```

**개선 방향:**

```typescript
// Built-in Tool은 순수 결과만 반환
async callTool(name: string, args: unknown): Promise<MCPResult<unknown>> {
  return createMCPSuccessToolResult('Success');
  // → { content: [...], isError: false }
}

// Worker에서 전송 계층 래핑
function wrapAsResponse(result: MCPResult, id: string): MCPResponse {
  return { jsonrpc: '2.0', id, result };
}
```

## 현재의 상태 / 문제점

### 문제 1: 아키텍처 불일치

**Built-in Tool의 특성:**

- Web Worker 내부에서 동작
- postMessage로 통신 (이미 직렬화됨)
- stdio 프로토콜 불필요

**현재 구현:**

- External MCP와 동일하게 `MCPResponse<unknown>` 반환
- 각 Built-in Server가 개별적으로 `jsonrpc`, `id` 필드 생성
- 5개 서버 × 평균 10개 함수 = 50+ 곳에서 중복 래핑

### 문제 2: WebMCPServer 인터페이스

**파일:** `src/lib/mcp-types.ts` (legacy) 또는 관련 타입 파일

```typescript
export interface WebMCPServer {
  name: string;
  displayName: string;
  description: string;
  category: 'automation' | 'storage' | 'planning' | 'execution';
  version?: string;
  tools: MCPTool[];
  callTool(name: string, args: unknown): Promise<MCPResponse<unknown>>; // ❌ 문제
}
```

**문제점:**

- `MCPResponse` 반환 → 전송 계층 책임을 서버에 부여
- 서버마다 `id` 생성 로직 중복 (`createId()` 호출)
- `jsonrpc: '2.0'` 하드코딩 중복

### 문제 3: Response Factory 함수 중복

**5개 Built-in 서버에서 공통 패턴:**

```typescript

// mcp-manager/server.ts (Line 493, 513, 518, ...)

```

**총 38개 에러 응답 인스턴스:**

- ui-tools: 6개
- playbook-store: 14개
- mcp-manager: 12개
- bootstrap-server: 2개
- planning-server: 1개

모두 `createMCPTextResponse()` 또는 `createMCPErrorResponse()` 사용

### 문제 4: mcp-worker의 단순 중계 역할

**파일:** `src/lib/web-mcp/mcp-worker.ts` (Lines 147-220)

```typescript
async function handleMCPMessage(
  message: WebMCPMessage,
): Promise<MCPResponse<unknown>> {
  switch (type) {
    case 'callTool': {
      const server = getMCPServer(serverName!);
      const response = await server.callTool(toolName!, args); // MCPResponse
      return response; // ← 그대로 전달만 함
    }
  }
}
```

**문제:**

- Worker가 아무런 가치 추가 없이 중계만 수행
- 전송 계층 래핑 책임이 서버에 분산되어 있음

## 🔴 Rust Built-in Tools MCPResponse 아키텍처 문제 (미해결)

> **⚠️ 주요 발견:** Web MCP 리팩토링과 유사한 문제가 Rust Built-in Tools에도 존재합니다.
> 이 섹션은 별도 리팩토링 계획 문서 작성 대상입니다.

### Rust Builtin Tools의 아키텍처 문제점

**문제 범위:**

- **관련 Rust 파일:** `src-tauri/src/mcp/builtin/` (workspace, content_store 등)
- **영향 범위:** Content Store, Workspace Tools 등 Rust 기반 builtin tool 서버
- **Tauri 커맨드:** `call_builtin_tool` (src-tauri/src/commands/mcp_commands.rs)
- **프론트엔드:** `src/lib/backend/builtin-tools.ts` 에서 호출

### 핵심 문제 사항

#### 1. Rust에서도 MCPResponse 직접 생성

- Rust builtin tool handlers가 직접 MCPResponse 구조 생성
- Web MCP와 동일하게 `jsonrpc: '2.0'`, `id` 필드를 각 handler에서 생성
- 전송 계층 래핑 책임이 서버에 분산

#### 2. 불명확한 에러 처리

- Rust Result 패턴 사용
- Frontend와 Protocol-level error 구분 불명확
- 일관성 있는 에러 포맷 부재

#### 3. 타입 정의의 모호성

- `src/lib/backend/types.ts`: `BuiltinServerInfo` 등 타입 정의
- `call_builtin_tool` return type이 명확하지 않음
- Web MCP와의 타입 불일치

### 해결 방향

**웹 MCP와 동일한 패턴 적용:**

1. Rust builtin handlers → `MCPResult` 반환 (전송 계층 제외)
2. Tauri Command layer → `MCPResponse` 래핑 담당
3. Frontend → 동일한 MCPResponse 구조 수신

**예상 수정 범위:**

- Rust builtin handler 함수: 50+ 곳
- 타입 정의: 5-10 곳
- 테스트: 20+ 케이스
- Tauri 커맨드 wrapper 추가

> ⚠️ **상세 분석과 계획은 별도 문서 `refactoring_rust_builtin_20251116_2130.md`에 작성됩니다.**
