# Refactoring Plan: Legacy Code Removal (Post-Migration)

**Date**: 2024-12-26  
**Target Version**: 0.4.0  
**Branch**: dev/0.4.0  
**Status**: Planning

---

## Executive Summary

이 Refactoring Plan은 LibrAgent의 V1 아키텍처(Web Worker MCP + IndexedDB)에서 V2 아키텍처(Rust Backend + SQLite)로의 Migration 완료 후, 더 이상 사용되지 않는 Legacy 코드를 안전하게 제거하는 작업을 다룬다.

**예상 소요 시간**: 4-6 시간  
**영향 범위**: Frontend Codebase, Dependencies, Build Output  
**Risk Level**: Medium (기존 V2 세션에는 영향 없음, V1 호환성 유지가 필요한 경우 위험 증가)

---

## 1. 작업의 목적

Rust Backend로의 Migration(V2)이 완료됨에 따라, 더 이상 사용되지 않는 Frontend 기반의 Legacy 시스템(Web MCP, IndexedDB, Local Services)을 제거하여:

- **코드베이스 경량화**: 미사용 코드 제거로 가독성 향상
- **빌드 크기 감소**: 불필요한 의존성 제거 (약 200KB 예상)
- **유지보수 부담 감소**: 이중 구현체 제거로 혼동 방지
- **런타임 성능 개선**: 미사용 초기화 로직 제거

---

## 2. 배경 및 맥락

### 2.1. V1 vs V2 아키텍처

| 항목              | V1 (Legacy)               | V2 (Current)                |
| ----------------- | ------------------------- | --------------------------- |
| **MCP 실행 환경** | Browser Web Worker        | Rust Native Process (Tokio) |
| **데이터 저장소** | IndexedDB (Dexie.js)      | SQLite (sqlx)               |
| **도구 실행**     | Frontend JS (비동기 제약) | Rust Backend (고성능)       |
| **세션 격리**     | 불완전 (메모리 공유)      | 완전 (Process 분리)         |
| **성능**          | 낮음 (브라우저 제약)      | 높음 (Native 코드)          |

### 2.2. Migration Status

다음 컴포넌트들이 V2로 완전히 포팅되었음을 전제로 한다:

- ✅ `BootstrapServer` (Rust)
- ✅ `KnowledgeServer` (Rust + SQLite FTS5)
- ✅ `PlanningServer` (Rust + SQLite)
- ✅ `PlaybookServer` (Rust + SQLite)
- ✅ `AssistantServer` (Rust + SQLite)
- ✅ `UiServer` (Rust + Handlebars)
- ✅ `WorkspaceServer` (Rust)
- ✅ `ContentStoreServer` (Rust)

### 2.3. 현재의 상태 / 문제점

### 2.3. 현재의 상태 / 문제점

- **Dual Implementation**: 동일한 기능(예: 세션 관리, 도구 실행)에 대해 Rust Backend와 Frontend Legacy 구현이 공존하고 있음.
- **Dead Code**: `src/lib/web-mcp`, `src/lib/db` 등 V2 세션에서는 전혀 사용되지 않는 코드가 남아있음.
- **Bundle Size**: 사용하지 않는 라이브러리(`dexie` ~80KB, Web Worker 번들 ~120KB)가 포함되어 빌드 크기를 불필요하게 증가시킴.
- **Confusion**: 개발자가 V1(Legacy)과 V2(Rust) 로직을 혼동하여 잘못된 수정을 할 위험이 있음.
- **Circular Dependencies**: Legacy 코드가 여전히 일부 Context에서 참조되고 있어 완전한 제거가 불가능한 상태.

**영향받는 파일 (의존성 검색 결과)**:

- `src/context/SessionContext.tsx` → `LocalSessionService`
- `src/context/AssistantContext.tsx` → `AssistantService`, `LocalDatabase`
- `src/context/MCPServerRegistryContext.tsx` → `McpServerService`
- `src/context/MCPServerContext.tsx` → `dbUtils`
- `src/context/WebMCPContext.tsx` → `WebMCPProxy`, `MCPWorker`
- `src/app/App.tsx` → `WebMCPProvider`, `WebMCPServiceRegistry`

## 3. 관련 코드의 구조 및 동작 방식 Summary

### 3.1. Legacy 아키텍처 다이어그램

```
Frontend (React)
    ↓
SessionContext → LocalSessionService
    ↓                    ↓
WebMCPContext ←→ WebMCPProxy ←→ Web Worker (MCP)
    ↓                             ↓
IndexedDB (Dexie) ←──────────────┘
```

### 3.2. V2 아키텍처 다이어그램

```
Frontend (React)
    ↓
rust-backend-client.ts (Tauri IPC)
    ↓
Rust Backend (AgentSessionManager)
    ↓
MCPServiceProxyManager
    ├─ BuiltinMCPServer (ui, knowledge, planning...)
    └─ External MCP (stdio)
    ↓
SQLite (sqlx)
```

### 3.3. Legacy 시스템 구조

- **Web MCP (`src/lib/web-mcp/`)**: 브라우저 Web Worker 위에서 동작하던 MCP 서버 구현체. 현재 Rust Backend의 `BuiltinMCPServer`로 기능이 이관됨.
  - `mcp-worker.ts`: Worker 진입점
  - `mcp-proxy.ts`: Main Thread ↔ Worker 통신 프록시
  - `modules/*/`: 각 MCP 서버 구현 (knowledge, planning, playbook, ui 등)
- **IndexedDB Layer (`src/lib/db/`)**: `Dexie.js`를 사용한 브라우저 로컬 DB. Rust Backend의 `SQLite`로 데이터 저장소가 변경됨.
  - `database.ts`: DB 스키마 정의 (assistants, mcpServers, sessions, messages, playbooks 테이블)
  - `service.ts`: Dexie 기반 DB 서비스 인스턴스
  - `crud.ts`: Generic CRUD 구현체
- **Legacy Services (`src/lib/services/`)**: IndexedDB를 직접 조작하던 서비스 클래스들.
  - `session-service.ts`: `LocalSessionService` 클래스
  - `assistant-service.ts`: `LocalAssistantService` + BM25 검색
  - `mcp-server-service.ts`: `LocalMcpServerService`
- **Contexts (`src/context/`)**: 일부 Context가 여전히 Legacy Service를 직접 인스턴스화하여 사용 중.

## 4. 변경 이후의 상태 / 해결 판정 기준

### 4.1. 성공 기준 (Success Criteria)

- ✅ **Clean Architecture**: Frontend는 오직 `rust-backend-client.ts` 또는 Tauri Command를 통해서만 데이터 및 로직에 접근해야 함.
- ✅ **No Legacy Directories**: `src/lib/web-mcp`, `src/lib/db`, `src/lib/search/bm25.ts` 디렉토리/파일이 존재하지 않아야 함.
- ✅ **Updated Dependencies**: `package.json`에서 `dexie` 의존성이 제거되어야 함.
- ✅ **Build Success**: Legacy 코드 제거 후에도 `pnpm build`가 에러 없이 성공해야 함.
- ✅ **Runtime Stability**: 애플리케이션 실행 시:
  - V2 세션 생성 정상 동작
  - 채팅 메시지 송수신 정상 동작
  - Rust Backend 도구 호출(UI 도구 포함) 정상 동작
  - 에러 로그 없음

    expect(buildOutput).not.toContain('dexie');
    expect(buildOutput).not.toContain('WebMCPProxy');
  });
});

## 9. 주의사항 및 위험 요소

### 9.1. Breaking Changes

- **V1 세션 데이터 손실**: IndexedDB에 저장된 기존 세션은 접근 불가능해짐.
  - **대응**: 사전에 V1 → V2 데이터 마이그레이션 스크립트 실행 필요 (별도 작업)

### 9.2. Rollback 전략

만약 배포 후 심각한 문제 발견 시:

1. Git Revert: `git revert <commit-hash>`
2. 긴급 패치: Legacy 코드를 일시적으로 복구
3. Hotfix Branch: 문제 해결 후 재배포

### 9.3. 점진적 제거 전략 (대안)

만약 한 번에 제거하기 위험하다면:

1. **Phase 1**: Legacy 코드를 `deprecated/` 폴더로 이동 (빌드에서 제외)
2. **Phase 2**: 1주일간 모니터링
3. **Phase 3**: 문제 없으면 완전 삭제

## 10. Clarification Q-list

### Q1: V1 세션 데이터 마이그레이션 상태

- **질문**: IndexedDB에 저장된 기존 V1 세션 데이터를 SQLite로 마이그레이션하는 작업이 완료되었는가?
- **영향**: 완료되지 않았다면, Legacy 코드 삭제 전에 마이그레이션 스크립트를 먼저 실행해야 함.
- **판단 기준**: `src-tauri/src/commands/migration_commands.rs` 등 마이그레이션 관련 코드 존재 여부 확인.

### Q2: AssistantContext의 BM25 검색 대체

- **질문**: Rust Backend의 `AssistantServer`에서 FTS5 기반 검색 기능을 제공하는가?
- **영향**: 제공하지 않는다면, `AssistantContext`의 검색 로직을 임시로 Frontend에 남겨야 할 수 있음.
- **확인 방법**: `src-tauri/src/mcp/builtin/assistant/mod.rs`에서 `searchAssistants` 도구 구현 여부 확인.

### Q3: MCPServerEntity 관리 Backend API

- **질문**: MCP 서버 설정(MCPServerEntity) CRUD 작업을 Rust Backend에서 지원하는 Tauri Command가 존재하는가?
- **영향**: 없다면 `MCPServerRegistryContext` 리팩토링이 불가능하며, 임시로 Local Service를 유지해야 함.
- **확인 방법**: `src-tauri/src/commands/mcp_commands.rs`에서 관련 Command 존재 여부 확인.

### Q4: Settings Service 대체

- **질문**: `src/lib/services/settings-service.ts`는 `db.objects`를 사용하는가?
- **영향**: 사용한다면 이 파일도 제거 대상에 포함되어야 하며, Settings를 Rust Backend로 이관해야 함.
- **확인 방법**: `settings-service.ts` 코드 검토.

### Q5: 점진적 제거 vs 일괄 제거

- **질문**: 한 번에 모든 Legacy 코드를 제거할 것인가, 아니면 `deprecated/` 폴더로 이동 후 점진적으로 제거할 것인가?
- **영향**: 점진적 제거는 안전하지만 작업 기간이 길어짐.
- **권장**: 충분한 테스트가 완료되었다면 일괄 제거, 불확실하다면 점진적 제거.
